# AGENTS.md — tethered

## What is tethered

tethered is a zero-dependency Python library for runtime network egress control. It uses `sys.addaudithook` (PEP 578) to intercept outbound socket connections and enforce an allow list of permitted destinations. One function call, no sidecar containers, no infrastructure changes.

```python
import tethered

tethered.activate(allow=["*.stripe.com:443", "db.internal:5432"])
```

### Module responsibilities

- **`_policy.py`** is pure logic. `AllowPolicy` is deeply immutable after construction and thread-safe to read: rules are `NamedTuple`s of strings and integers (a network is stored as integers), and the matching methods read plain-tuple copies of the rule fields, so nothing can be reassigned in place. It handles hostname wildcards (`*.stripe.com`), CIDR ranges (`10.0.0.0/8`), port filtering (`host:443`), and localhost detection. It also keeps every parsed rule in allow-list order (`_parsed_rules`) and classifies one rule of a scope against a global policy (`_check_rule_overlap`, which answers "unknown" where the relation is not certain: `scope()` reports nothing then); `scope()` pairs that with the rule text for its overlap warnings, so a rule string is parsed in exactly one place. Malformed rules raise `ValueError` at construction. Its only side effect is logging (a warning, once per rule per process, for an address-shaped wildcard such as `10.*`), and it has no imports beyond stdlib (`fnmatch`, `ipaddress`, `logging`, `re`, `typing`, `unicodedata`).

- **`_core.py`** owns the audit hook lifecycle. It installs a single `sys.addaudithook` that intercepts: (1) socket events — `socket.getaddrinfo`, `socket.gethostbyname`/`gethostbyaddr` (DNS-level policy + IP↔hostname mapping; `socket.getnameinfo` is deliberately not handled, because its event carries no flags), `socket.connect`/`sendto`/`sendmsg` (connection policy; a `sendmsg` event that carries `None` for the address is a write on a connected socket, names no destination and passes, which is how asyncio's selector transports write from Python 3.12), and `socket.__new__` (no enforcement — two one-time warnings about event loops the hook cannot see into: on Windows when a `ProactorEventLoop` is running, since that loop raises no connect events (`_warn_if_proactor_loop`), and elsewhere when uvloop is loaded, since a uvloop event loop raises no audit event for its connections, lookups, datagrams and process launches (`_warn_if_uvloop`, which looks for `uvloop` in `sys.modules` and never imports it; it serves the two cases in which tethered runs next to a loaded uvloop, a log-only policy and a `scope()` with no policy under it, is also called from `activate()` and on scope entry, and the lower-case flag `_uvloop_warning_pending` starts clear on Windows)); (2) process-launch events — `subprocess.Popen`, `os.system`, `os.exec*`, `os.posix_spawn`, `os.spawn*`, `os.startfile`, plus `_winapi.CreateProcess` and (Python 3.14+) `_posixsubprocess.fork_exec` for launches that bypass `subprocess.Popen` such as `multiprocessing` workers (launch classification, `external_subprocess_policy` enforcement, establishing the policy payload in the child's launch environment, locked-mode payload-integrity check, scope-to-subprocess propagation via frame-locals mutation in `_execute_child`). An explicit environment that merely lacks the policy variable is completed where that is possible, under a lock too, where it used to be refused: a `subprocess.Popen` launch gets the variable through the copy of the environment `_execute_child` is given, for an external program as well under a lock (whatever Python that program starts has to inherit the policy; refused only if the frame write fails), and an `os.exec*` of this interpreter is carried out by the hook itself with the variable added (`_exec_with_policy`: an exec does not return, so the hook can make the same call with a completed copy of the environment, and a failed exec leaves the hook as the caller's own error). The same call hands an active scope on: the hook runs in the context that entered the scope, also in a forked child, so an exec of this interpreter made inside a scope is carried out with the scope chain in the payload (inherited environment or explicit, with a policy or with scopes only), which is how a child launched under gevent's `Popen` receives it. `os.posix_spawn` and `os.spawn*` have no such way: refused under a lock, external otherwise. A different or invalid value and two spellings of the key are refused under a lock on every route; (3) `os.putenv`/`os.unsetenv` of the policy variable, which `os.environ` does not show (tracked in the `_env_dirty` flag); a change made from another interpreter or below Python shows up in neither, so under a lock a launch that inherits the environment also asks the guardian for the variable as the process holds it (`_process_env_differs`, the `"foreign"` state of `_process_env_state`); (4) FS events in locked mode — `os.remove`, `os.rename`, `open` (write-mode), `os.chmod`, `os.truncate`, `os.link`, `os.symlink`, `_winapi.CopyFile2` (refuses tampering with `tethered.pth`, and creating a `tethered.start` beside it, which from Python 3.15 switches the `.pth` import line off). Both files are recognised by their name and their directory (`_path_matches_pth`): by the text of the path first, then by the identity of its directory (`os.stat`, taken against the event's `dir_fd` where it carries one), so a symlink or junction to the directory, a Windows short name and the descriptor-relative calls `shutil.rmtree` makes on POSIX all name the hook, and a file of that name elsewhere does not, unless it is the same file: for the events that change a file in place (write-mode `open`, `os.chmod`, `os.truncate`, `_winapi.CopyFile2`) and for the source of a rename, `_path_matches_pth(..., same_file=True)` also compares the file itself, because uv installs by hard-linking out of its cache and the hook is then a `tethered.pth` in the cache directory as well. `os.link` / `os.symlink` with the hook as their source are refused (`_gives_pth_another_name`): a write through a name that does not mention `tethered.pth` is never looked at, so a further name is stopped where it is made. An event none of whose arguments mentions `tethered.` ends at one substring test (`_mentions_hook`), which is what the `open` of any other file costs under a lock, and only a path that ends in one of the two names is looked up in the file system. `_WINDOWS_PATH_RULES` says whether a path is read the way Windows reads it (tests flip it, as they do `_ENV_NAMES_IGNORE_CASE`). Not matched: a name of another spelling that existed before the lock, `/proc/self/fd/N` on Linux, and `os.open(..., dir_fd=...)`, whose event carries no descriptor. What gets past the guard is met by a check of the hook's content: a `tethered.pth` is the hook only while it holds `_PTH_BOOTSTRAP`, the one line tethered installs (`_is_bootstrap_file`; a test compares the constant with `src/tethered.pth`). `_compute_pth_path` takes the first of `_pth_candidates` with that content, `activate()` warns through `_stand_in_pth_path` when a file of that name is there with another (a second distribution that ships a `tethered.pth` replaces ours on installation, and neither pip nor uv says so), and `_launch_exclusion` reads the file again for every launch that would inherit, so a hook that was emptied, removed or replaced since makes that launch external (`_HOOK_CHANGED_REASON`); under a lock `_handle_subprocess` refuses it outright, whatever `external_subprocess_policy` says (`_HOOK_LOST_REASONS`), as it refuses a launch whose process environment lost the policy variable. From Python 3.15 a `tethered.start` beside the hook switches its import line off (`_START_FILE_SILENCES_PTH`, which tests flip): `_start_file_beside` finds one that got there in a way the guard could not refuse (`os.mknod`, another process, before the policy), `_compute_pth_path` then finds no hook and `activate()` warns through `_silenced_pth_path`, and a launch is treated as with a changed hook (`_HOOK_SILENCED_REASON`). The read raises an `open` event of its own; a locked policy that has failed its integrity check is refused it, and `_is_bootstrap_file` then answers False without passing the refusal on (`activate()` over such a policy is refused by the guardian, as `TetheredLocked`); (5) `import` events, while a policy that is not log-only is active: an import of uvloop or pycares is refused with `ImportError` (`_refuse_import`). `_REFUSED_IMPORTS` maps the event names to the library, two each (`uvloop` and `uvloop.loop`, `pycares` and `pycares._cares`), because `import x` raises an event for the package and `importlib.import_module("x")` only for what the package's `__init__` imports. Both libraries do their networking where no audit event is raised, and what prefers them falls back to Python's `socket` module when the import fails (uvicorn to the standard asyncio event loop, aiohttp to its threaded resolver). The refusal is logged once per library (`_IMPORT_REFUSALS`, `_import_refusals_logged`: a warning for uvloop, info for pycares), and a library that is not installed is left to Python's own "No module named" (`_is_installed`, which asks `importlib.util.find_spec`). A uvloop that is already loaded is the business of `activate()`, which logs `_UVLOOP_LOADED_MSG` at error level and raises it as `RuntimeError` for every policy that is not log-only, before anything is changed; a pycares that is already loaded is left alone. The module has three once-per-process messages besides the Proactor warning, each behind a lower-case flag that is cleared before logging: `_warn_if_uvloop` (`_uvloop_warning_pending`), `_warn_if_fork_server_runs` (`_fork_server_warning_pending`: `activate()` warns when multiprocessing's fork server, looked up in `sys.modules` and never imported, was started before the policy, because its workers are copies of it and hold no policy), and `_hint_at_unnamed_address` (`_unnamed_address_hint_pending`: the first refused connection to an IP address that no hostname is known for, under a policy with hostname rules, says that the name may have been looked up outside Python's `socket` module). All per-activation state (`policy`, `log_only`, `fail_closed`, `on_blocked`, `locked`, `external_subprocess_policy`, `_serialized_payload`, `_global_payload_dict`, `_pth_path`, `_local_hostname`) is bundled into a frozen `_Config` dataclass; a hook reads `_config` once and works from that object, which eliminates TOCTOU bugs between fields. The lock token is not in `_Config`: only the C guardian holds it. `activate()` and `deactivate()` are serialized from start to finish by the re-entrant `_lifecycle_lock` and are all-or-nothing; `_state_lock` only guards the one-time hook installation. Across the interpreters of the process they take turns through `_activation_claim`, the C guardian's process-wide claim: it is taken after `_lifecycle_lock`, before the question whether a policy is locked is asked, and held until the transition is committed or undone, so an interpreter that waited while another one locked a policy gets `TetheredLocked` before it has written anything. A refusal under a lock is worded by `_locked_refusal` for where the caller stands: the holder without its token and an interpreter with a locked config of its own (one that joined) get the messages that ask for the token, and an interpreter that is neither (`_c_guardian.holds_lock()` is false and its `_config` is `None` or unlocked) gets `_OUTSIDE_THE_LOCK_MSG`, which says that it is outside the lock and that no token will help. Every write tethered makes to the policy variable happens with the claim held (`_propagate_policy_to_env`, `_clear_policy_from_env`, `_restore_policy_env`), including the launch hook's re-assertion of an unlocked payload: `_reassert_policy_env` takes `_lifecycle_lock` and the claim, in that order, and writes only if the config is still the active one. Each use of the claim is a `with` inside a `try` whose `finally` calls `_activation_claim.restore(held)` with the count `held()` gave before: the `with` alone can leave the claim taken (Python 3.14 raises a pending exception between `__enter__` and the block and never calls `__exit__`), and a claim that is never given up stops every later transition in the process. Without the extension `_UnsharedClaim`, a lock of the interpreter's own, stands in. `_join_locked(payload)` is what the bootstrap of an interpreter created under a lock calls: it rebuilds the policy and a locked `_Config` from the guardian's copy of the payload, with the functions `activate()` uses, and offers them to `_c_guardian.join()`; it writes nothing to the variable, takes no token, and `_config` is bound only by a successful join. All of this module's state is per interpreter: each interpreter has its own `_core`. The IP-to-hostname map is an `OrderedDict` with LRU eviction, guarded by `_ip_map_lock`; `deactivate()` drops it, and so does an `activate()` whose serialized payload differs from the previous one, while an `activate()` that puts the same policy in place again keeps it (a thread between its lookup and its connect would otherwise be refused an allowed host). The hook is installed once and can never be removed — after `deactivate()`, `_config` is `None` and the hook is a no-op. `_install_hook()` confirms the hook is live with the private audit event `tethered.hook_probe` (the hook answers through the list passed with it; `_audit_hook` tests `_ENV_AND_PROBE_EVENTS`, and `_ENV_EVENTS` remains the list to keep in step with the C `classify_event`) and raises `RuntimeError` when another audit hook refused it. Context-local scopes are managed by a `_ScopeConfig` dataclass, a `_scopes` `ContextVar` holding a per-context scope stack, and the `scope` class (usable as both a context manager and a decorator); entries are pushed and removed by identity (`_push_scope`/`_pop_scope`), and `_active_scope_count` counts them process-wide. The `_check_scopes` and `_enforce_scope_block` helpers are called from the audit hook to intersect scope rules with the global policy. `_build_integrity_snapshot` generates the list of facts the C guardian pins in locked mode. The log line for what a layer does not allow says `blocked`, or `would block` when the layer is log-only and the call goes ahead (`_refusal_verb`). `_launch_exclusion(event, args)` is the launch classifier: `None` for a Python child that inherits, `""` for a launch of something else, and for a launch of `sys.executable` that counts as external the reason (`_site_bypass_reason` for the interpreter options), which ends the warning and `SubprocessBlocked.description`. `_SYS_EXECUTABLE_IS_PYTHON` is false where Python is embedded and `sys.executable` is not an interpreter (`_sys_executable_is_python`: `sys.orig_argv` is empty and the name is not `python…` / `pypy…`, which is uWSGI and not mod_wsgi): every launch is then external (`_NOT_AN_INTERPRETER_REASON`) and `activate()` logs a warning that names `--py-sys-executable`. Where a process can fork, `_reinit_locks_after_fork` (an `os.register_at_fork` handler, defined on POSIX only) resets this module's locks in the child, in place, so that a lock another thread held at the fork does not hang the child; a re-entrant lock the forking thread holds is left to it. `EgressBlocked` and `SubprocessBlocked` also accept their message alone (`cls(*exc.args)`, how Celery's JSON result serializer rebuilds an exception): the sentinel `_NOT_GIVEN` tells that call from one that passes a port, `_message_alone` rejects anything that is not a message, and `_egress_fields` / `_subprocess_fields` read the attributes back out of it. The constructors write their text as literals and do not share constants with those readers: the guardian builds these exceptions when it refuses over a tampered module, so their text must not depend on what those constants are bound to (`test_rebinding_any_pinned_module_global_is_detected` fails otherwise).

- **`_autoactivate.py`** runs at interpreter startup, via `tethered.pth`, in every Python interpreter (the main interpreter of a process and each subinterpreter) whose `site.py` processes that file and whose environment carries `_TETHERED_CHILD_POLICY`. It first takes its turn through `_core._activation_claim`, so that it meets an `activate()` / `deactivate()` under way in another interpreter before or after it and never in the middle, and then goes by the variable as the process holds it (`process_policy_env()`); if the process no longer holds it, nothing is established. Where it cannot wait (the claim raises `RuntimeError` before the turn was taken: this thread is inside another interpreter's transition, or Python is shutting down) it goes by the value its own `os.environ` showed at startup. Reads the variable (nested JSON: `{"global": {...}, "scopes": [...]}`), validates the payload schema (exact types), calls `tethered.activate(**global)` if a non-null global is present, then pushes inherited scopes onto the `_scopes` ContextVar of the context the child starts in (no `__exit__` ever fires — they stay for the child's lifetime, but like any scope they are context-local, not a process-wide floor). When the inherited global has `locked` or `fail_closed` set and the policy cannot be established, it raises `SystemExit` so the interpreter does not start (`site.py` swallows ordinary exceptions from a `.pth` line); otherwise it logs a warning and continues. A lock exists once per process, so an interpreter that starts inside a process which already holds one (a subinterpreter) does not activate a policy of its own. Before the variable is parsed, `_join_locked_policy()` asks the guardian for a locked payload (`locked_payload()`) and, if there is one, joins the lock through `_core._join_locked()`: the global policy then comes from the guardian's record, only `scopes` is read from the variable, and the rest of the bootstrap is strict whatever the variable says. A join that fails is logged as one warning and never stops startup (up to Python 3.12 a `SystemExit` there ends the whole process); the bootstrap then goes by the variable as when nothing is locked, and the guardian refuses that interpreter the guarded operations while the lock is held. Where no lock is held, and after a failed join, a subinterpreter establishes an inherited `locked` policy unlocked (`_establish_unlocked`, which binds a `_Config` directly and never writes the process-wide policy variable). Every other strict failure stops a subinterpreter's startup too. Idempotent (skips if `_config` is already set, which is the fork-mode case where state is inherited via process-state copy).

- **`__init__.py`** re-exports the public API (`activate`, `deactivate`, `scope`, `EgressBlocked`, `TetheredLocked`, `SubprocessBlocked`). Nothing else lives here.

- **`_guardian.c`** is a C extension that provides tamper-resistant locked mode. It does NOT reimplement policy matching — all matching stays in Python. At `activate(locked=True)` it records a list of `(owner, name, kind)` facts that `_core._build_integrity_snapshot()` generates from the namespaces of `_core` and `_policy`: every module-level binding (except `_config` and lower-case scalar runtime state), every class attribute of the classes defined there, the `__code__` of every function, the absence of shadowed builtins and of `__getattribute__`/`__getattr__` hooks, and the class and every slot of the active `_Config` and `AllowPolicy`. It re-checks them, comparing pointers, on every socket audit event, every process-launch event, and — pre-filtered in C — filesystem events whose path mentions `tethered.pth` or `tethered.start` and `os.putenv`/`os.unsetenv` of the policy variable. Any mismatch (object replaced, method monkey-patched, frozen field mutated via `object.__setattr__`) refuses the operation — `EgressBlocked` for socket events, `SubprocessBlocked` for the others — and a tamper alert is written to fd 2. The C guardian also owns the lock state: it alone holds the token, `deactivate()` and `activate()` go through C for token verification, and it rebinds `_core._config` as part of its own commit, so swapping `_config` to an unlocked config doesn't help; a policy that fails the check can be neither replaced nor deactivated. It also owns the trusted DNS-resolution window (`resolve()`, calling the resolver captured when the interpreter took or joined the lock). Its hook sees the events of every interpreter and its lock is process-wide, held under the owner's interpreter ID (never its address, which a later interpreter can be given), while what it verifies are Python objects that belong to one interpreter each, so its state is split in two. Per interpreter, a `GuardianState` struct (role, snapshot, config, token, exception classes, resolver), found through the interpreter's ID and touched only with that interpreter's GIL held; structs are pooled and never freed. Process-wide, atomics for what the hook reads on every event (active, owner ID, the policy's `log_only`, `lock_generation`) and one spinlock (`state_mutex`) for the C-owned copy of the locked payload, the startup-window record and the list of structs; no Python API is called and nothing is allocated while it is held. Also process-wide is the activation claim (`claim_taken`, `claim_interp`, `claim_serial`; which thread holds it is thread-local), exposed to `_core` as the context manager `activation_claim`: the interpreter that is in the middle of an `activate()` or `deactivate()` holds it, so that no interpreter's write of the policy variable is under way while another one publishes and commits. A thread that finds it taken waits with its GIL released, with no time limit (in the main thread a signal handler that raises ends the wait); the holding thread may take it again; the same thread asking from another interpreter is refused with `RuntimeError`, as is a wait while Python shuts down; it is given up for an interpreter whose struct is given back while it holds it (`forfeit_claim`) and in a forked child whose thread did not hold it. `held()` and `restore()` let `_core` give up a claim that a `with` took and never released. An interpreter created under the lock joins it (`join()`), which is accepted only while that interpreter starts (the hook closes an interpreter's window at its `import sitecustomize` audit event, watched in every interpreter whether or not a policy is locked; interpreters that existed when the hook was first installed, and every interpreter of a `-S` process, never join), only once, never for the owner, and only for a config whose `_serialized_payload` equals the locked payload to the byte. A joined interpreter's guarded events take the owner's verification path against its own struct, except that `os.putenv`/`os.unsetenv` of the policy variable is refused outright, and it counts as joined only while the generation it recorded is current (the generation moves when the owner commits a different payload and when the lock is released). For every other interpreter the guardian touches no interpreter's objects (only atomics and the event's arguments) and refuses the guarded operations (`other_interpreter_event`), letting socket events pass under a `log_only` lock; an owner whose state is gone is refused everything guarded. `locked_payload()` returns the guardian's copy of the locked policy and `process_policy_env()` the policy variable as the process itself holds it. `holds_lock()` says whether the calling interpreter is the one that took the lock (a policy is locked and the owner ID is the caller's); `_core` uses it to tell the holder with a wrong token from an interpreter the lock does not belong to. The token is not reported to the garbage collector. When it adds its hook it confirms the hook is live with a private probe event and fails activation otherwise. The event lists in `classify_event` must stay in step with `_SUBPROCESS_EVENTS`, `_PTH_FS_EVENTS` and `_ENV_EVENTS` in `_core.py`. `locked=True` requires the C extension. The extension is always built during installation — a C compiler is required for source installs. It uses multi-phase initialisation, declares support for interpreters with their own GIL (Python 3.12+) and does not declare free-threading support. `docs/security.md` states what a join is worth (startup files are trusted) and which interpreters stay outside a lock; keep it in step with `join()` and the hook's dispatch.

### Key design decisions

1. **Fail-open by default, fail-closed optional.** If the matching logic itself raises an unexpected exception, the connection is allowed and a warning is logged (fail-open). Users can set `fail_closed=True` for stricter environments where errors should block rather than allow. The child bootstrap follows the same rule: a child that cannot establish an inherited policy logs a warning and continues, unless that policy has `locked` or `fail_closed` set, in which case it refuses to start. One case is deliberately different: a subinterpreter that cannot join the lock of its process starts anyway, with a warning. Refusing to start would end the whole process up to Python 3.12, and the interpreter is not left open: the guardian refuses it the guarded operations for as long as the lock is held.

2. **Audit hooks are irremovable.** `sys.addaudithook` has no corresponding remove function. This is a feature for security (malicious code can't unhook it) but means tests must use `deactivate()` or reset internal state directly in fixtures for cleanup rather than removing the hook.

3. **IP-to-hostname mapping via getaddrinfo interception.** When `socket.getaddrinfo("api.stripe.com", 443)` fires, we resolve it ourselves (with a reentrancy guard) and record the hostname under the canonical text of each resolved IP. The map value is a tuple of up to 8 hostnames per address, most recent first. When `socket.connect(sock, (resolved_ip, 443))` fires later, we look up the names and allow the connect if the policy allows any of them or the raw IP. `gethostbyname` records no mapping, only a candidate for the connect-time fallback search (`_fallback_resolve`), which runs on a map miss unless every layer already allows the raw IP.

4. **Thread safety.** `AllowPolicy` is deeply immutable. The `_Config` bundle is a frozen dataclass swapped by a single reference assignment, and `activate()`/`deactivate()` are serialized by the re-entrant `_lifecycle_lock` (`_state_lock` only guards hook installation). `_ip_to_hostname` is an `OrderedDict` guarded by `_ip_map_lock` with LRU eviction. `_active_scope_count` is guarded by `_scope_count_lock`. Reentrancy guard uses `contextvars.ContextVar` (async-safe, faster than `threading.local()`). All of that is per interpreter, like the module it lives in. Interpreters can run in parallel under their own GILs (Python 3.12+); what they share is in the C guardian, where a per-interpreter struct is only touched with its interpreter's GIL held and the process-wide state is atomics plus one spinlock, inside which no Python API is called and nothing is allocated. Their `activate()` / `deactivate()` calls take turns through the guardian's activation claim (lock order: `_lifecycle_lock`, then the claim), so when several interpreters lock a policy at the same moment one wins and each of the others gets `TetheredLocked` when its turn comes. None of this has been validated on free-threaded Python: the C extension does not declare free-threading support (the GIL is re-enabled when it is imported on a free-threaded build) and no free-threaded wheels are published.

5. **Zero runtime dependencies.** Everything uses stdlib only: `sys`, `os`, `_socket`, `threading`, `collections`, `contextvars`, `dataclasses`, `fnmatch`, `functools`, `importlib.util`, `inspect`, `ipaddress`, `json`, `logging`, `operator`, `re`, `reprlib`, `types`, `typing`, `unicodedata`, plus `site` (imported lazily) and, on Python 3.11–3.12 only, `ctypes` (imported lazily for `PyFrame_LocalsToFast`). The C extension (`_guardian.c`) uses only the CPython C API, the C standard library and a few operating-system calls (reading the process environment, yielding or briefly sleeping a thread, `pthread_atfork`); it links against no external library. Build dependencies (`setuptools`) are build-time only.

6. **Context-local scopes.** `scope()` uses `contextvars.ContextVar` to maintain a per-context stack of scope configurations, making it safe for concurrent use across threads and async tasks. Scopes use intersection semantics with the global policy — they can only narrow the set of allowed destinations, never widen it. `scope` works as both a context manager (`with tethered.scope(allow=[...]):`) and a decorator (`@tethered.scope(allow=[...])`); generator functions cannot be decorated. A scope exits by removing its own entry from the stack, by identity, not by restoring a snapshot, so out-of-order exits (a generator suspended inside a `with scope():` block) do not disturb other scopes. A process-wide count of active scope entries lets the hook record lookups made in threads that do not carry the scope (asyncio's executor).

7. **Tamper-resistant locked mode via C extension.** When `activate(locked=True)` is called, the C guardian records a snapshot generated from the `_core` and `_policy` namespaces and verifies it on every socket event, every process-launch event, and the guarded `tethered.pth` / policy-variable events. This catches `_config` replacement, rebinding of any module-level function or helper, method monkey-patching, `object.__setattr__` on the frozen config, and `__code__` swapping. It is not a sandbox, and `ctypes` is not the only way around it: builtins and the standard-library functions the policy calls, the contents of pinned containers (the IP map), function defaults and closures, and anything done before activation are outside the snapshot. The lock is one per process. An interpreter created while it is held joins it during its own startup, with a locked config built from the guardian's copy of the policy and a snapshot of its own modules, and is then verified like the owner; it has no token. An interpreter that did not join (it existed before the lock, its bootstrap did not run, its join failed, the process runs with `-S`, or the policy it joined has since been replaced or released) is refused the guarded operations. Joining is tied to startup because the guardian cannot authenticate the objects it is offered, so a joined interpreter is protected like a locked child process: its startup files are trusted. `docs/security.md` ("Locked mode — what it does and does not do") is the authoritative statement; update it whenever `_build_integrity_snapshot`, the guardian's event list or the rules for joining change.

8. **Subprocess auto-propagation via `tethered.pth`.** `activate()` writes a JSON-serialized policy to `os.environ["_TETHERED_CHILD_POLICY"]`, and the subprocess hook establishes the same payload in each Python child's launch environment (injected into an explicit `env=` of any mapping type, re-asserted in `os.environ` if it was cleaned, and for an `os.exec*` of this interpreter by carrying the exec out with a completed environment; locked mode does the same for an explicit environment that merely lacks the variable, and refuses one that carries another value and a process environment that lost it). Under a lock, an inherited environment is also compared with the variable as the process itself holds it, because `os.environ` is one interpreter's copy and shows neither another interpreter's change nor one made below Python. A Python interpreter runs `tethered._autoactivate` on startup when `tethered.pth` is in a site directory it processes — site-packages or the enabled user site, not an editable install's `src/`. The child re-engages tethered with the parent's policy before user code runs. The file counts as the bootstrap only while it holds tethered's own line, which is checked at `activate()` and again at each launch of a Python child (`_is_bootstrap_file`). The same bootstrap is how a subinterpreter of a locked process joins the lock (decision 7): the variable has to be present for the bootstrap to run, but the policy that is joined comes from the guardian, not from the variable. This covers `multiprocessing.Pool`, `ProcessPoolExecutor`, gunicorn/uvicorn workers, and plain `subprocess.run([sys.executable, ...])`. A worker that inherits an enforcing policy cannot load uvloop (decision 10), so a server that prefers uvloop runs such a worker on the standard loop; a worker that inherits a log-only policy can, and the audit hook then sees nothing that goes through its event loop, launches through `asyncio.create_subprocess_exec` included (see "Event loops" under Documentation). A policy reaches a process when it starts: workers that existed before `activate()`, and every worker of a multiprocessing fork server that was started before it, hold none. `external_subprocess_policy` (`warn`/`block`/`allow`, default `warn`) controls parent-side enforcement for launches that auto-inherit can't reach: non-Python tools, different Python interpreters, `sys.executable` with `-S` (the only site-bypass flag; `-s` and `-I` count only when the hook is in the per-user site-packages, and `-E` never does), a POSIX launch whose `argv[0]` is not `sys.executable`, interpreter options that cannot be parsed, any Python launch when no processed `tethered.pth` exists, a Python launch whose environment cannot be given the payload, and every launch where `sys.executable` is a program that embeds Python and not an interpreter (uWSGI without `--py-sys-executable`).

9. **Scope-to-subprocess propagation via frame-locals mutation.** `tethered.scope()` propagates to spawn-mode child processes: a child launched from inside `with scope(allow=[...])` inherits the parent's effective policy at the launch site (global ∩ scopes), not just the at-rest global. Implemented by mutating `subprocess.Popen._execute_child`'s `env` local from inside the `subprocess.Popen` audit hook (PEP 667 write-through proxy on 3.13+; `ctypes.pythonapi.PyFrame_LocalsToFast` on 3.11–3.12). The same mechanism injects the global payload when an explicit `env=` lacks it, with or without a scope. Race-free across threads because frame locals are per-call, not shared global state. Audit hooks are read-only on `args`, so frame-locals mutation is the only mechanism that satisfies the no-monkey-patch and no-opt-in constraints. An `os.exec*` of this interpreter is the one other route: there the hook carries the exec out itself with the scope in the environment (`_exec_with_policy`), which covers gevent's `Popen`. Limitation: scope cannot propagate through `os.system` / `os.startfile` / `os.spawn*` / `os.posix_spawn` (no env channel to inject) or through spawn-mode `multiprocessing` workers (they never reach `_execute_child`); those launches still receive the at-rest global only.

10. **Refuse to run where nothing would be enforced.** Where tethered knows that a policy would silently not be applied, it does not put it in place: `activate()` raises when its audit hook cannot be installed, and when uvloop is loaded (a uvloop event loop raises no audit event for anything it does, and uvicorn picks it whenever it is installed). While an enforcing policy is active it keeps uvloop from being imported, and pycares too (with c-ares, hosts allowed by name are refused and forbidden names still reach the name server), so that the servers and clients that prefer them fall back to what the hook sees. A log-only policy refuses nothing, these included, and a `scope()` without a policy only warns. This guards a deployment against being unenforced without anyone noticing; it is not a barrier to code that is out to get around tethered, which can load any other extension that does its own networking. What a real server does with each refusal (falls back, does not start, restarts its workers without end, or swallows the exception) was measured in the container suites and is in `docs/COMPATIBILITY.md`; a change to this behaviour has to be run against them.

## Conventions

### Code style

- Use `from __future__ import annotations` in all modules.
- Private modules are prefixed with `_` (e.g., `_core.py`, `_policy.py`).
- Type hints on all public function signatures.
- No docstrings on private helpers unless the logic is non-obvious.
- Keep modules small and focused. If a module exceeds ~500 lines, consider splitting.

- **Container suites** (`tests_containers/`): real servers, task queues and client libraries in Docker, on every supported Python version, with tethered installed from a wheel the way a user installs it. The container has no network; a "world" on its loopback interface counts every connection and datagram that arrives, and those counters are the ground truth: a test asserts what the application reported and what arrived. A test whose docstring starts with `Limit:` pins a known limit as what happens today. The pytest process never holds a policy. A suite is a directory under `suites/` (a `suite.toml`, a pinned `requirements.txt`, `test_*.py`); nothing else has to be edited to add one. - **The gating rule.** Run the container suites before merging a change to `src/tethered/_core.py`, `src/tethered/_autoactivate.py`, `src/tethered/_guardian.c`, `src/tethered.pth` or `setup.py`. CI runs them on every pull request that touches `src/`, `setup.py`, `pyproject.toml` or `tests_containers/` (`.github/workflows/container-tests.yml`), and weekly with `--unpinned` against the latest release of every requirement. `docs/COMPATIBILITY.md` is written from these suites: when a suite's result changes, change the page with it, and when a new version changes what tethered has to do, write that down where the behaviour is documented before changing the test.
- Run core tests: `uv run pytest tests/ -v`
- Run with coverage: `uv run pytest tests/ -v --cov`
- Run example tests (requires network): `uv run pytest tests_examples/ -v`
- Run the container suites (requires Docker): `uv run python tests_containers/run.py` for everything, `--suite uvicorn --python 3.13` for one run, `-k EXPR` for pytest's filter, `--verbose` for the output of passing runs, `--list` for the suites
- **Example tests** (`tests_examples/test_examples.py`): Run each `examples/*.py` as a subprocess. They make real HTTP calls to `api.github.com`. Not included in coverage (subprocesses aren't measured). Kept in a separate directory to avoid affecting coverage thresholds. `tests_examples/conftest.py` copies `tethered.pth` into site-packages for the session, as `tests/conftest.py` does: without the hook in a site directory, examples 11 and 12 would have their own Python children treated as external.
- **Adding a new example**: when adding `examples/<NN>_*.py`, register it in `EXAMPLE_SCRIPTS` in `tests_examples/test_examples.py`. The list is intentionally explicit (not a glob) so draft scripts don't enter the test rotation. Each registered example must exit with code 0 on the happy path, produce stdout, and print the literal token `(unexpected)` on any branch that should have been blocked by tethered — the test asserts `(unexpected)` is NOT present, so a tethered regression that allows a blocked call surfaces immediately.
- Core tests that need DNS resolution (log-only, fail-open, IP map tests) are marked `@requires_network` and skip automatically if DNS is unavailable. The majority of core tests run fully offline.
- **Microbenchmark** (`benchmarks/overhead.py`): Standalone, zero-dep script measuring per-event wall-clock overhead — `socket.connect` (TCP, against a daemon-thread accept-and-close listener on 127.0.0.1), `socket.getaddrinfo`, `sys.audit` synthetic event, and `with tethered.scope(...)` enter+exit — across deactivated / activated / activated+scope / activated+locked. Run with `uv run python benchmarks/overhead.py` (default 5k per-event iterations, 3k TCP iterations with a median-of-3 to reject load-spike outliers on Windows where the connect baseline is ~700 µs vs ~30 µs on Linux) or `--iterations N`. Not part of the test suite; intended for ad-hoc measurement.

The script names one cppcheck release and the commit of its tag, and builds it from the upstream source; CI runs the same hook, so there is no second copy of cppcheck to keep in step.
- Pre-commit hooks run ruff, bandit, ty, interrogate, markdownlint, and cppcheck on every commit, and commitizen on commit messages. Ruff, bandit, ty, interrogate and commitizen run as local hooks via `uv run`, so the hooks, the commands above and CI all use the one version of each that `uv.lock` pins; upgrade a tool with `uv lock --upgrade-package <name>`, not in `.pre-commit-config.yaml`. Cppcheck runs via Docker (builds a `tethered-cppcheck:<version>` image on first use, which takes a minute or two); upgrade it by changing `CPPCHECK_VERSION` and `CPPCHECK_COMMIT` in `scripts/cppcheck.sh`. Tests run in CI only (not in pre-commit) to avoid conflicts with `uv.lock` during version bumps. The remaining third-party hooks (pre-commit-hooks, markdownlint-cli2) are pinned by commit SHA for supply-chain integrity, and `uv.lock` records the hash of every Python tool. Install with `uv run pre-commit install --hook-type pre-commit --hook-type commit-msg`.
- CI runs `pre-commit run --all-files` (lint job, includes ty and cppcheck) and the full test matrix. Both jobs install with `uv sync --locked`, which fails when `uv.lock` does not match `pyproject.toml`, so CI runs the versions the lock names or does not run. The lint job runs on the interpreter `.python-version` names, and each cell of the test matrix sets `UV_PYTHON` and checks that `uv run` is on its own Python (see Python version support). The lint job keeps the cppcheck image in the Actions cache under the hash of `scripts/cppcheck.sh`, so cppcheck is compiled once per version and not once per run. The publish job uses `cibuildwheel` to build platform-specific wheels with the compiled C extension. GitHub Actions are pinned by commit SHA. The workflow uses `permissions: { contents: read }` for least privilege. A separate CodeQL workflow scans both Python and C/C++ code on push to main, on PRs, and weekly. A third workflow, `container-tests.yml`, runs the container suites, one job per suite and Python version (see Testing). A fourth, `docs.yml`, builds the documentation site on every push and pull request and publishes it from `main` (see Documentation).

### What NOT to do

- Do not add runtime dependencies. This library must remain zero-dep. The C extension uses the CPython C API, the C standard library and a few operating-system calls (no external C libraries).
- Do not monkey-patch `socket.socket` or any other stdlib class. The audit hook API is the only interception mechanism.
- Do not catch `EgressBlocked` inside tethered itself (except in tests). It must propagate to the caller.
- Do not add framework-specific code (Django, Flask, etc.) to the core package. Framework integrations belong in documentation, not code.
- Do not add features speculatively. Every addition must serve a concrete, current use case.
- Do not stage or commit changes. The developer reviews and commits manually.

### Adding new allow rule types

If adding a new rule type (e.g., regex patterns, deny lists):

1. Add a new `_XxxRule` `NamedTuple` in `_policy.py` with primitive fields only (strings and integers), plus a plain-tuple fields slot on `AllowPolicy` that the matching methods read. Rules must stay deeply immutable: the locked-mode guardian pins the identity of each policy slot, not what is reachable through it.
2. Parse it in `AllowPolicy.__init__`, appending exactly one parsed rule per allow-list entry to `parsed_rules`: the scope overlap warnings pair `_parsed_rules` with the allow list by position.
3. Check it in `is_allowed()` or `_check_hostname()`/`_check_ip()`.
4. Serialize it in `_serialize_allow_list()` (`_core.py`) so that child processes rebuild the same rule; the serialized form must re-parse to an identical policy.
5. Classify it in `AllowPolicy._check_rule_overlap()`, so that `scope()` overlap warnings understand the new kind. Return "unknown" for whatever cannot be decided for certain; a guess would be logged as a fact.
6. Add unit tests in `test_policy.py` first, then integration tests if needed.

- Links, by file: the README and `SECURITY.md` use relative paths to files of the repository; cross-references between docs/ files use relative paths; `CHANGELOG.md`, which the site includes as a page of its own, and `PYPI.md` use absolute URLs.
- **Source style: one line per paragraph.** Do not hard-wrap prose, list items, or blockquote text at a column limit — write each paragraph (and each list item) on a single source line. CommonMark / GFM collapse soft line-breaks to spaces, so the rendered output is identical either way; the single-line form gives cleaner git diffs (a one-word edit doesn't churn the whole paragraph) and avoids re-wrap busywork. Code blocks (fenced and indented), tables, headings, link-reference definitions (`[label]: url`), and HTML blocks are left verbatim.

### Python version support

- Python 3.11–3.15. `sys.addaudithook` was added in 3.8, so this is well within range.
- The bootstrap is an `import` line in `tethered.pth`. PEP 829 (Python 3.15) deprecates such lines in favour of `<name>.start` entry-point files: they still run on 3.15–3.17 unless a `<name>.start` file sits beside the `.pth`, and Python 3.18 is to ignore them. tethered ships no `tethered.start`; locked mode refuses creating one, and one that is there all the same is found at `activate()` and at each launch of a Python child. `test_cpython_ignores_a_pth_import_line_beside_a_start_file` in `tests/test_guardian.py` pins that behaviour and will fail on 3.18.
- Do not use syntax or features unavailable in 3.11 (e.g., no `type` statement from 3.12).
- `.python-version` names the development interpreter, 3.14, and says nothing about what tethered supports (that is `requires-python`). A plain `uv sync` or `uv run` in a checkout builds the project environment on it, so the pre-commit hooks run on it too, and the CI jobs outside the test matrix install it with a bare `uv python install` (lint, CodeQL, the sdist build, and the docs build, where `uvx` does not read the file and takes that Python as the only one uv has installed). uv holds the project environment to the file: a `uv run` in an environment built on another version removes it and builds it again on 3.14, whatever `uv sync --python X.Y` was told before. The test job of `ci.yml` therefore sets `UV_PYTHON` to the version of its cell, which outranks the file, and a step fails the cell when `uv run` is on another Python; without the variable every cell would test 3.14 and pass. Keep both when that job changes. To run on another version locally, use `uv run --isolated --python X.Y pytest tests/`, which leaves the project environment alone, or an environment of its own (`UV_PROJECT_ENVIRONMENT`) with `UV_PYTHON=X.Y` set for every uv command; `uv run --no-sync` uses an environment as it is and only warns. The container suites and cibuildwheel are not affected by the file: an image, or an interpreter, of the version under test does the build.
