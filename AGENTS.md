# AGENTS.md — tethered

## What is tethered

tethered is a zero-dependency Python library for runtime network egress control. It uses `sys.addaudithook` (PEP 578) to intercept outbound socket connections and enforce an allow list of permitted destinations. One function call, no sidecar containers, no infrastructure changes.

```python
import tethered

tethered.activate(allow=["*.stripe.com:443", "db.internal:5432"])
```

### Module responsibilities

- **`_policy.py`** is pure logic. `AllowPolicy` is deeply immutable after construction and thread-safe to read: rules are `NamedTuple`s of strings and integers (a network is stored as integers), and the matching methods read plain-tuple copies of the rule fields, so nothing can be reassigned in place. It handles hostname wildcards (`*.stripe.com`), CIDR ranges (`10.0.0.0/8`), port filtering (`host:443`), and localhost detection. It also keeps every parsed rule in allow-list order (`_parsed_rules`) and classifies one rule of a scope against a global policy (`_check_rule_overlap`, which answers "unknown" where the relation is not certain: `scope()` reports nothing then); `scope()` pairs that with the rule text for its overlap warnings, so a rule string is parsed in exactly one place. Malformed rules raise `ValueError` at construction. Its only side effect is logging (a warning, once per rule per process, for an address-shaped wildcard such as `10.*`), and it has no imports beyond stdlib (`fnmatch`, `ipaddress`, `logging`, `re`, `typing`, `unicodedata`).

- **`_core.py`** owns the audit hook lifecycle. It installs a single `sys.addaudithook` that intercepts: (1) socket events — `socket.getaddrinfo`, `socket.gethostbyname`/`gethostbyaddr` (DNS-level policy + IP↔hostname mapping; `socket.getnameinfo` is deliberately not handled, because its event carries no flags), `socket.connect`/`sendto`/`sendmsg` (connection policy; a `sendmsg` event that carries `None` for the address is a write on a connected socket, names no destination and passes, which is how asyncio's selector transports write from Python 3.12; the connect with which `socket.socketpair()` joins its own two sockets where the platform has none of its own, Windows, where every asyncio event loop makes one, passes too: `_is_own_socketpair_connect` recognises it by the frame that called `connect()`, which has to run `_SOCKETPAIR_FALLBACK_CODE` (the code object of `socket._fallback_socketpair`, taken at import), by a target of 127.0.0.1 or ::1, and by that frame's `lsock` listening on exactly that address, read through the methods of the C type (macOS cannot say whether a socket listens, so there it never passes; its `socketpair()` is native); it is asked only where a layer refuses the address, and before the fallback search), and `socket.__new__` (no enforcement — two one-time warnings about event loops the hook cannot see into: on Windows when a `ProactorEventLoop` is running, since that loop raises no connect events (`_warn_if_proactor_loop`), and elsewhere when uvloop is loaded, since a uvloop event loop raises no audit event for its connections, lookups, datagrams and process launches (`_warn_if_uvloop`, which looks for `uvloop` in `sys.modules` and never imports it; it serves the two cases in which tethered runs next to a loaded uvloop, a log-only policy and a `scope()` with no policy under it, is also called from `activate()` and on scope entry, and the lower-case flag `_uvloop_warning_pending` starts clear on Windows)); (2) process-launch events — `subprocess.Popen`, `os.system`, `os.exec*`, `os.posix_spawn`, `os.spawn*`, `os.startfile`, plus `_winapi.CreateProcess` and (Python 3.14+) `_posixsubprocess.fork_exec` for launches that bypass `subprocess.Popen` such as `multiprocessing` workers (launch classification, `external_subprocess_policy` enforcement, establishing the policy payload in the child's launch environment, locked-mode payload-integrity check, scope-to-subprocess propagation via frame-locals mutation in `_execute_child`). An explicit environment that merely lacks the policy variable is completed where that is possible, under a lock too, where it used to be refused: a `subprocess.Popen` launch gets the variable through the copy of the environment `_execute_child` is given, for an external program as well under a lock (whatever Python that program starts has to inherit the policy; refused only if the frame write fails), and an `os.exec*` of this interpreter is carried out by the hook itself with the variable added (`_exec_with_policy`: an exec does not return, so the hook can make the same call with a completed copy of the environment, and a failed exec leaves the hook as the caller's own error). The same call hands an active scope on: the hook runs in the context that entered the scope, also in a forked child, so an exec of this interpreter made inside a scope is carried out with the scope chain in the payload (inherited environment or explicit, with a policy or with scopes only), which is how a child launched under gevent's `Popen` receives it. `os.posix_spawn` and `os.spawn*` have no such way: refused under a lock, external otherwise. A different or invalid value and two spellings of the key are refused under a lock on every route; (3) `os.putenv`/`os.unsetenv` of the policy variable, which `os.environ` does not show (tracked in the `_env_dirty` flag); a change made from another interpreter or below Python shows up in neither, so under a lock a launch that inherits the environment also asks the guardian for the variable as the process holds it (`_process_env_differs`, the `"foreign"` state of `_process_env_state`); (4) FS events in locked mode — `os.remove`, `os.rename`, `open` (write-mode), `os.chmod`, `os.truncate`, `os.link`, `os.symlink`, `_winapi.CopyFile2` (refuses tampering with `tethered.pth`, and creating a `tethered.start` beside it, which from Python 3.15 switches the `.pth` import line off). Both files are recognised by their name and their directory (`_path_matches_pth`): by the text of the path first, then by the identity of its directory (`os.stat`, taken against the event's `dir_fd` where it carries one), so a symlink or junction to the directory, a Windows short name and the descriptor-relative calls `shutil.rmtree` makes on POSIX all name the hook, and a file of that name elsewhere does not, unless it is the same file: for the events that change a file in place (write-mode `open`, `os.chmod`, `os.truncate`, `_winapi.CopyFile2`) and for the source of a rename, `_path_matches_pth(..., same_file=True)` also compares the file itself, because uv installs by hard-linking out of its cache and the hook is then a `tethered.pth` in the cache directory as well. `os.link` / `os.symlink` with the hook as their source are refused (`_gives_pth_another_name`): a write through a name that does not mention `tethered.pth` is never looked at, so a further name is stopped where it is made. An event none of whose arguments mentions `tethered.` ends at one substring test (`_mentions_hook`), which is what the `open` of any other file costs under a lock, and only a path that ends in one of the two names is looked up in the file system. `_WINDOWS_PATH_RULES` says whether a path is read the way Windows reads it (tests flip it, as they do `_ENV_NAMES_IGNORE_CASE`). Not matched: a name of another spelling that existed before the lock, `/proc/self/fd/N` on Linux, and `os.open(..., dir_fd=...)`, whose event carries no descriptor. What gets past the guard is met by a check of the hook's content: a `tethered.pth` is the hook only while it holds `_PTH_BOOTSTRAP`, the one line tethered installs (`_is_bootstrap_file`; a test compares the constant with `src/tethered.pth`). `_compute_pth_path` takes the first of `_pth_candidates` with that content, `activate()` warns through `_stand_in_pth_path` when a file of that name is there with another (a second distribution that ships a `tethered.pth` replaces ours on installation, and neither pip nor uv says so), and `_launch_exclusion` reads the file again for every launch that would inherit, so a hook that was emptied, removed or replaced since makes that launch external (`_HOOK_CHANGED_REASON`); under a lock `_handle_subprocess` refuses it outright, whatever `external_subprocess_policy` says (`_HOOK_LOST_REASONS`), as it refuses a launch whose process environment lost the policy variable. From Python 3.15 a `tethered.start` beside the hook switches its import line off (`_START_FILE_SILENCES_PTH`, which tests flip): `_start_file_beside` finds one that got there in a way the guard could not refuse (`os.mknod`, another process, before the policy), `_compute_pth_path` then finds no hook and `activate()` warns through `_silenced_pth_path`, and a launch is treated as with a changed hook (`_HOOK_SILENCED_REASON`). The read raises an `open` event of its own; a locked policy that has failed its integrity check is refused it, and `_is_bootstrap_file` then answers False without passing the refusal on (`activate()` over such a policy is refused by the guardian, as `TetheredLocked`); (5) `import` events, while a policy that is not log-only is active: an import of uvloop or pycares is refused with `ImportError` (`_refuse_import`). `_REFUSED_IMPORTS` maps the event names to the library, two each (`uvloop` and `uvloop.loop`, `pycares` and `pycares._cares`), because `import x` raises an event for the package and `importlib.import_module("x")` only for what the package's `__init__` imports. Both libraries do their networking where no audit event is raised, and what prefers them falls back to Python's `socket` module when the import fails (uvicorn to the standard asyncio event loop, aiohttp to its threaded resolver). The refusal is logged once per library (`_IMPORT_REFUSALS`, `_import_refusals_logged`: a warning for uvloop, info for pycares), and a library that is not installed is left to Python's own "No module named" (`_is_installed`, which asks `importlib.util.find_spec`). A uvloop that is already loaded is the business of `activate()`, which logs `_UVLOOP_LOADED_MSG` at error level and raises it as `RuntimeError` for every policy that is not log-only, before anything is changed; a pycares that is already loaded is left alone. The module has three once-per-process messages besides the Proactor warning, each behind a lower-case flag that is cleared before logging: `_warn_if_uvloop` (`_uvloop_warning_pending`), `_warn_if_fork_server_runs` (`_fork_server_warning_pending`: `activate()` warns when multiprocessing's fork server, looked up in `sys.modules` and never imported, was started before the policy, because its workers are copies of it and hold no policy), and `_hint_at_unnamed_address` (`_unnamed_address_hint_pending`: the first refused connection to an IP address that no hostname is known for, under a policy with hostname rules, says that the name may have been looked up outside Python's `socket` module). All per-activation state (`policy`, `log_only`, `fail_closed`, `on_blocked`, `locked`, `external_subprocess_policy`, `_serialized_payload`, `_global_payload_dict`, `_pth_path`, `_local_hostname`) is bundled into a frozen `_Config` dataclass; a hook reads `_config` once and works from that object, which eliminates TOCTOU bugs between fields. The lock token is not in `_Config`: only the C guardian holds it. `activate()` and `deactivate()` are serialized from start to finish by the re-entrant `_lifecycle_lock` and are all-or-nothing; `_state_lock` only guards the one-time hook installation. Across the interpreters of the process they take turns through `_activation_claim`, the C guardian's process-wide claim: it is taken after `_lifecycle_lock`, before the question whether a policy is locked is asked, and held until the transition is committed or undone, so an interpreter that waited while another one locked a policy gets `TetheredLocked` before it has written anything. A refusal under a lock is worded by `_locked_refusal` for where the caller stands: the holder without its token and an interpreter with a locked config of its own (one that joined) get the messages that ask for the token, and an interpreter that is neither (`_c_guardian.holds_lock()` is false and its `_config` is `None` or unlocked) gets `_OUTSIDE_THE_LOCK_MSG`, which says that it is outside the lock and that no token will help. Every write tethered makes to the policy variable happens with the claim held (`_propagate_policy_to_env`, `_clear_policy_from_env`, `_restore_policy_env`), including the launch hook's re-assertion of an unlocked payload: `_reassert_policy_env` takes `_lifecycle_lock` and the claim, in that order, and writes only if the config is still the active one. Each use of the claim is a `with` inside a `try` whose `finally` calls `_activation_claim.restore(held)` with the count `held()` gave before: the `with` alone can leave the claim taken (Python 3.14 raises a pending exception between `__enter__` and the block and never calls `__exit__`), and a claim that is never given up stops every later transition in the process. `import tethered` loads no C extension: `_load_guardian()` imports it and binds `_c_guardian` and `_activation_claim` (the claim first), once, at the start of `activate()`, `deactivate()`, `_join_locked()` and the startup bootstrap, before `_lifecycle_lock` and the claim are taken; `scope()` never loads it. The hook's own uses of `_c_guardian` (`_handle_getaddrinfo`, `_fallback_resolve`, `_process_env_differs`) matter only once a policy is in place in that interpreter, which comes after a load: an interpreter that has only entered scopes resolves through `_socket.getaddrinfo`, which is what `resolve()` serves an interpreter outside a lock under a `log_only` policy, and under an enforcing lock the guardian's hook refuses its lookups and launches before tethered's Python hook runs. It binds them only while `_c_guardian` is `None`, so a test's stand-in, and once a policy is locked the pinned guardian, stays as it is; `_guardian_load_pending` (unpinned runtime state) makes the import happen once, and an error of the import other than `ImportError` is raised to the caller and tried again at the next call. Until the load, and without the extension, `_UnsharedClaim`, a lock of the interpreter's own, stands in, and `_c_guardian` is `None`. `_join_locked(payload)` is what the bootstrap of an interpreter created under a lock calls: it rebuilds the policy and a locked `_Config` from the guardian's copy of the payload, with the functions `activate()` uses, and offers them to `_c_guardian.join()`; it writes nothing to the variable, takes no token, and `_config` is bound only by a successful join. All of this module's state is per interpreter: each interpreter has its own `_core`. The IP-to-hostname map is an `OrderedDict` with LRU eviction, guarded by `_ip_map_lock`; `deactivate()` drops it, and so does an `activate()` whose serialized payload differs from the previous one, while an `activate()` that puts the same policy in place again keeps it (a thread between its lookup and its connect would otherwise be refused an allowed host). The hook is installed once and can never be removed — after `deactivate()`, `_config` is `None` and the hook is a no-op. `_install_hook()` confirms the hook is live with the private audit event `tethered.hook_probe` (the hook answers through the list passed with it; `_audit_hook` tests `_ENV_AND_PROBE_EVENTS`, and `_ENV_EVENTS` remains the list to keep in step with the C `classify_event`) and raises `RuntimeError` when another audit hook refused it. Context-local scopes are managed by a `_ScopeConfig` dataclass, a `_scopes` `ContextVar` holding a per-context scope stack, and the `scope` class (usable as both a context manager and a decorator); entries are pushed and removed by identity (`_push_scope`/`_pop_scope`), and `_active_scope_count` counts them process-wide. The `_check_scopes` and `_enforce_scope_block` helpers are called from the audit hook to intersect scope rules with the global policy. `_build_integrity_snapshot` generates the list of facts the C guardian pins in locked mode. The log line for what a layer does not allow says `blocked`, or `would block` when the layer is log-only and the call goes ahead (`_refusal_verb`). `_launch_exclusion(event, args)` is the launch classifier: `None` for a Python child that inherits, `""` for a launch of something else, and for a launch of `sys.executable` that counts as external the reason (`_site_bypass_reason` for the interpreter options), which ends the warning and `SubprocessBlocked.description`. `_SYS_EXECUTABLE_IS_PYTHON` is false where Python is embedded and `sys.executable` is not an interpreter (`_sys_executable_is_python`: `sys.orig_argv` is empty and the name is not `python…` / `pypy…`, which is uWSGI and not mod_wsgi): every launch is then external (`_NOT_AN_INTERPRETER_REASON`) and `activate()` logs a warning that names `--py-sys-executable`. Where a process can fork, `_reinit_locks_after_fork` (an `os.register_at_fork` handler, defined on POSIX only) resets this module's locks in the child, in place, so that a lock another thread held at the fork does not hang the child; a re-entrant lock the forking thread holds is left to it. Importing tethered does not register it: `_watch_forks()` does, once (`_fork_handler_pending`, unpinned runtime state, cleared after the registration), called from `_load_guardian()` and from `_install_hook()` before either takes a lock, which is before the first of the locks it resets is taken on every route (a `scope()` included). `_REGISTER_AT_FORK` is `os.register_at_fork` where it exists and `None` elsewhere, a constant tests flip. `EgressBlocked` and `SubprocessBlocked` also accept their message alone (`cls(*exc.args)`, how Celery's JSON result serializer rebuilds an exception): the sentinel `_NOT_GIVEN` tells that call from one that passes a port, `_message_alone` rejects anything that is not a message, and `_egress_fields` / `_subprocess_fields` read the attributes back out of it. The constructors write their text as literals and do not share constants with those readers: the guardian builds these exceptions when it refuses over a tampered module, so their text must not depend on what those constants are bound to (`test_rebinding_any_pinned_module_global_is_detected` fails otherwise).

- **`_autoactivate.py`** runs at interpreter startup, via `tethered.pth`, in every Python interpreter (the main interpreter of a process and each subinterpreter) whose `site.py` processes that file and whose environment carries `_TETHERED_CHILD_POLICY`. It first loads the C guardian (`_claim_and_guardian()` calls `_core._load_guardian()`, whatever the payload holds) and takes its turn through `_core._activation_claim`, so that it meets an `activate()` / `deactivate()` under way in another interpreter before or after it and never in the middle, and then goes by the variable as the process holds it (`process_policy_env()`); if the process no longer holds it, nothing is established. Where it cannot wait (the claim raises `RuntimeError` before the turn was taken: this thread is inside another interpreter's transition, or Python is shutting down) it goes by the value its own `os.environ` showed at startup. Reads the variable (nested JSON: `{"global": {...}, "scopes": [...]}`), validates the payload schema (exact types), calls `tethered.activate(**global)` if a non-null global is present, then pushes inherited scopes onto the `_scopes` ContextVar of the context the child starts in (no `__exit__` ever fires — they stay for the child's lifetime, but like any scope they are context-local, not a process-wide floor). When the inherited global has `locked` or `fail_closed` set and the policy cannot be established, it raises `SystemExit` so the interpreter does not start (`site.py` swallows ordinary exceptions from a `.pth` line); otherwise it logs a warning and continues. A lock exists once per process, so an interpreter that starts inside a process which already holds one (a subinterpreter) does not activate a policy of its own. Before the variable is parsed, `_join_locked_policy()` asks the guardian for a locked payload (`locked_payload()`) and, if there is one, joins the lock through `_core._join_locked()`: the global policy then comes from the guardian's record, only `scopes` is read from the variable, and the rest of the bootstrap is strict whatever the variable says. A join that fails is logged as one warning and never stops startup (up to Python 3.12 a `SystemExit` there ends the whole process); the bootstrap then goes by the variable as when nothing is locked, and the guardian refuses that interpreter the guarded operations while the lock is held. Where no lock is held, and after a failed join, a subinterpreter establishes an inherited `locked` policy unlocked (`_establish_unlocked`, which binds a `_Config` directly and never writes the process-wide policy variable). Every other strict failure stops a subinterpreter's startup too. Idempotent (skips if `_config` is already set, which is the fork-mode case where state is inherited via process-state copy).

- **`__init__.py`** re-exports the public API (`activate`, `deactivate`, `scope`, `EgressBlocked`, `TetheredLocked`, `SubprocessBlocked`). Nothing else lives here.

- **`__main__.py`** is the command line, `python -m tethered`, with one command, `check`, which runs `_check.run(sys.stdout)`. argparse: a usage error exits with 2, and the check exits with 0 whatever it finds. No other options (no `--json`, no `--strict`).

- **`_check.py`** is the preflight check, for the owner of an application, run in the environment where the application runs: which rows of `docs/COMPATIBILITY.md` apply there, before anything is enforced. `findings()` returns `Finding`s (group, what is there, what it means, what to do, links to headings of the documentation site), in five groups (`GROUPS`): event loops (uvloop importable, Windows' `ProactorEventLoop`), name resolution (pycares / aiodns, dnspython, gevent with `GEVENT_RESOLVER` naming ares first, eventlet unless `EVENTLET_NO_GREENDNS` is `yes`, which is how each library reads its variable), client libraries (the rows of `_clients.py` all of whose distributions are installed; rows that share a result, a mechanism and the advice in `_CLIENT_ADVICE` make one finding), child processes (the bootstrap, `sys.executable` or uWSGI installed, multiprocessing on POSIX before 3.14, forkserver as the default start method) and the interpreter (a free-threaded build, the C extension missing). `render()` lays the report out as plain text and `run()` writes it. It changes nothing: no policy, no audit hook, no network call, no write, and no import of a third-party module. Distributions are found with `importlib.metadata` (`_installed()`, through the `_distributions` indirection that tests replace), modules with `_core._is_installed` (`find_spec`, which imports nothing for a top-level name), the default start method with `multiprocessing.get_all_start_methods()[0]`, which fixes nothing. The bootstrap is judged by `_core`'s own helpers in the order `activate()` asks them (`_compute_pth_path`, `_stand_in_pth_path`, `_silenced_pth_path`, `_start_file_beside`): they open the candidate files for reading and log nothing. The platform facts are module constants (`_WINDOWS`, `_POSIX`, `_PYTHON`, `_FREE_THREADED`) so that tests can flip them on every platform; `_core._SYS_EXECUTABLE_IS_PYTHON` is read where it is. Every statement it prints is one the documentation makes, in its terms: a finding says what is installed and what the page measured for it in a named arrangement, never that the application uses that arrangement. Change the wording with the page it comes from.

- **`_clients.py`** is data: the rows of the `TABLE` of `tests_containers/suites/clients/catalog.py` whose result is not "enforced" (id, title, result, packages, mechanism), in the catalogue's order. That directory is not part of the package, so the package carries this copy; `tests/test_check.py` compares the two.

- **`_guardian.c`** is a C extension that provides tamper-resistant locked mode. It does NOT reimplement policy matching — all matching stays in Python. At `activate(locked=True)` it records a list of `(owner, name, kind)` facts that `_core._build_integrity_snapshot()` generates from the namespaces of `_core` and `_policy`: every module-level binding (except `_config` and lower-case scalar runtime state), every class attribute of the classes defined there, the `__code__` of every function, the absence of shadowed builtins and of `__getattribute__`/`__getattr__` hooks, and the class and every slot of the active `_Config` and `AllowPolicy`. It re-checks them, comparing pointers, on every socket audit event, every process-launch event, and — pre-filtered in C — filesystem events whose path mentions `tethered.pth` or `tethered.start` and `os.putenv`/`os.unsetenv` of the policy variable. Any mismatch (object replaced, method monkey-patched, frozen field mutated via `object.__setattr__`) refuses the operation — `EgressBlocked` for socket events, `SubprocessBlocked` for the others — and a tamper alert is written to fd 2. The C guardian also owns the lock state: it alone holds the token, `deactivate()` and `activate()` go through C for token verification, and it rebinds `_core._config` as part of its own commit, so swapping `_config` to an unlocked config doesn't help; a policy that fails the check can be neither replaced nor deactivated. It also owns the trusted DNS-resolution window (`resolve()`, calling the resolver captured when the interpreter took or joined the lock). Its hook sees the events of every interpreter and its lock is process-wide, held under the owner's interpreter ID (never its address, which a later interpreter can be given), while what it verifies are Python objects that belong to one interpreter each, so its state is split in two. Per interpreter, a `GuardianState` struct (role, snapshot, config, token, exception classes, resolver), found through the interpreter's ID and touched only with that interpreter's GIL held; structs are pooled and never freed. Process-wide, atomics for what the hook reads on every event (active, owner ID, the policy's `log_only`, `lock_generation`) and one spinlock (`state_mutex`) for the C-owned copy of the locked payload, the startup-window record and the list of structs; no Python API is called and nothing is allocated while it is held. Also process-wide is the activation claim (`claim_taken`, `claim_interp`, `claim_serial`; which thread holds it is thread-local), exposed to `_core` as the context manager `activation_claim`: the interpreter that is in the middle of an `activate()` or `deactivate()` holds it, so that no interpreter's write of the policy variable is under way while another one publishes and commits. A thread that finds it taken waits with its GIL released, with no time limit (in the main thread a signal handler that raises ends the wait); the holding thread may take it again; the same thread asking from another interpreter is refused with `RuntimeError`, as is a wait while Python shuts down; it is given up for an interpreter whose struct is given back while it holds it (`forfeit_claim`) and in a forked child whose thread did not hold it. `held()` and `restore()` let `_core` give up a claim that a `with` took and never released. An interpreter created under the lock joins it (`join()`), which is accepted only while that interpreter starts (the hook closes an interpreter's window at its `import sitecustomize` audit event, watched in every interpreter whether or not a policy is locked; interpreters that existed when the hook was first installed, and every interpreter of a `-S` process, never join), only once, never for the owner, and only for a config whose `_serialized_payload` equals the locked payload to the byte. A joined interpreter's guarded events take the owner's verification path against its own struct, except that `os.putenv`/`os.unsetenv` of the policy variable is refused outright, and it counts as joined only while the generation it recorded is current (the generation moves when the owner commits a different payload and when the lock is released). For every other interpreter the guardian touches no interpreter's objects (only atomics and the event's arguments) and refuses the guarded operations (`other_interpreter_event`), letting socket events pass under a `log_only` lock; an owner whose state is gone is refused everything guarded. `locked_payload()` returns the guardian's copy of the locked policy and `process_policy_env()` the policy variable as the process itself holds it. `holds_lock()` says whether the calling interpreter is the one that took the lock (a policy is locked and the owner ID is the caller's); `_core` uses it to tell the holder with a wrong token from an interpreter the lock does not belong to. The token is not reported to the garbage collector. When it adds its hook it confirms the hook is live with a private probe event and fails activation otherwise. The event lists in `classify_event` must stay in step with `_SUBPROCESS_EVENTS`, `_PTH_FS_EVENTS` and `_ENV_EVENTS` in `_core.py`. `locked=True` requires the C extension. The extension is always built during installation — a C compiler is required for source installs. It uses multi-phase initialisation, declares support for interpreters with their own GIL (Python 3.12+) and does not declare free-threading support. It is imported on first need (`_core._load_guardian()`), not with tethered, and importing it is what claims the interpreter's struct and registers the `pthread_atfork` handlers; an interpreter that never imported it has no struct and stands outside a lock like one whose struct has no role. `docs/security.md` states what a join is worth (startup files are trusted) and which interpreters stay outside a lock; keep it in step with `join()` and the hook's dispatch.

### Key design decisions

1. **Fail-open by default, fail-closed optional.** If the matching logic itself raises an unexpected exception, the connection is allowed and a warning is logged (fail-open). Users can set `fail_closed=True` for stricter environments where errors should block rather than allow. The child bootstrap follows the same rule: a child that cannot establish an inherited policy logs a warning and continues, unless that policy has `locked` or `fail_closed` set, in which case it refuses to start. One case is deliberately different: a subinterpreter that cannot join the lock of its process starts anyway, with a warning. Refusing to start would end the whole process up to Python 3.12, and the interpreter is not left open: the guardian refuses it the guarded operations for as long as the lock is held.

2. **Audit hooks are irremovable.** `sys.addaudithook` has no corresponding remove function. This is a feature for security (malicious code can't unhook it) but means tests must use `deactivate()` or reset internal state directly in fixtures for cleanup rather than removing the hook.

3. **IP-to-hostname mapping via getaddrinfo interception.** When `socket.getaddrinfo("api.stripe.com", 443)` fires, we resolve it ourselves (with a reentrancy guard) and record the hostname under the canonical text of each resolved IP. The map value is a tuple of up to 8 hostnames per address, most recent first. When `socket.connect(sock, (resolved_ip, 443))` fires later, we look up the names and allow the connect if the policy allows any of them or the raw IP. `gethostbyname` records no mapping, only a candidate for the connect-time fallback search (`_fallback_resolve`), which runs on a map miss unless every layer already allows the raw IP.

4. **Thread safety.** `AllowPolicy` is deeply immutable. The `_Config` bundle is a frozen dataclass swapped by a single reference assignment, and `activate()`/`deactivate()` are serialized by the re-entrant `_lifecycle_lock` (`_state_lock` only guards hook installation). `_ip_to_hostname` is an `OrderedDict` guarded by `_ip_map_lock` with LRU eviction. `_active_scope_count` is guarded by `_scope_count_lock`. Reentrancy guard uses `contextvars.ContextVar` (async-safe, faster than `threading.local()`). All of that is per interpreter, like the module it lives in. Interpreters can run in parallel under their own GILs (Python 3.12+); what they share is in the C guardian, where a per-interpreter struct is only touched with its interpreter's GIL held and the process-wide state is atomics plus one spinlock, inside which no Python API is called and nothing is allocated. Their `activate()` / `deactivate()` calls take turns through the guardian's activation claim (lock order: `_lifecycle_lock`, then the claim), so when several interpreters lock a policy at the same moment one wins and each of the others gets `TetheredLocked` when its turn comes. None of this has been validated on free-threaded Python: the C extension does not declare free-threading support (the GIL is re-enabled when it is loaded on a free-threaded build: `import tethered` and `scope()` leave the GIL off, and `activate()`, `deactivate()` and the startup bootstrap, which load the extension, re-enable it) and no free-threaded wheels are published.

5. **Zero runtime dependencies.** Everything uses stdlib only: `sys`, `os`, `_socket`, `socket`, `threading`, `collections`, `contextvars`, `dataclasses`, `fnmatch`, `functools`, `importlib.util`, `inspect`, `ipaddress`, `json`, `logging`, `operator`, `re`, `reprlib`, `types`, `typing`, `unicodedata`, plus `site` (imported lazily) and, on Python 3.11–3.12 only, `ctypes` (imported lazily for `PyFrame_LocalsToFast`). The command line (`__main__.py`, `_check.py`) adds `argparse`, `importlib.metadata`, `multiprocessing`, `shutil`, `sysconfig` and `textwrap`. The C extension (`_guardian.c`) uses only the CPython C API, the C standard library and a few operating-system calls (reading the process environment, yielding or briefly sleeping a thread, `pthread_atfork`); it links against no external library. `import tethered` loads no C extension and registers no fork handler: both happen on first use (`_load_guardian()`, `_watch_forks()`). Build dependencies (`setuptools`) are build-time only.

6. **Context-local scopes.** `scope()` uses `contextvars.ContextVar` to maintain a per-context stack of scope configurations, making it safe for concurrent use across threads and async tasks. Scopes use intersection semantics with the global policy — they can only narrow the set of allowed destinations, never widen it. `scope` works as both a context manager (`with tethered.scope(allow=[...]):`) and a decorator (`@tethered.scope(allow=[...])`); generator functions cannot be decorated. A scope exits by removing its own entry from the stack, by identity, not by restoring a snapshot, so out-of-order exits (a generator suspended inside a `with scope():` block) do not disturb other scopes. A process-wide count of active scope entries lets the hook record lookups made in threads that do not carry the scope (asyncio's executor).

7. **Tamper-resistant locked mode via C extension.** When `activate(locked=True)` is called, the C guardian records a snapshot generated from the `_core` and `_policy` namespaces and verifies it on every socket event, every process-launch event, and the guarded `tethered.pth` / policy-variable events. This catches `_config` replacement, rebinding of any module-level function or helper, method monkey-patching, `object.__setattr__` on the frozen config, and `__code__` swapping. It is not a sandbox, and `ctypes` is not the only way around it: builtins and the standard-library functions the policy calls, the contents of pinned containers (the IP map), function defaults and closures, and anything done before activation are outside the snapshot. The lock is one per process. An interpreter created while it is held joins it during its own startup, with a locked config built from the guardian's copy of the policy and a snapshot of its own modules, and is then verified like the owner; it has no token. An interpreter that did not join (it existed before the lock, its bootstrap did not run, its join failed, the process runs with `-S`, or the policy it joined has since been replaced or released) is refused the guarded operations. Joining is tied to startup because the guardian cannot authenticate the objects it is offered, so a joined interpreter is protected like a locked child process: its startup files are trusted. `docs/security.md` ("Locked mode — what it does and does not do") is the authoritative statement; update it whenever `_build_integrity_snapshot`, the guardian's event list or the rules for joining change.

8. **Subprocess auto-propagation via `tethered.pth`.** `activate()` writes a JSON-serialized policy to `os.environ["_TETHERED_CHILD_POLICY"]`, and the subprocess hook establishes the same payload in each Python child's launch environment (injected into an explicit `env=` of any mapping type, re-asserted in `os.environ` if it was cleaned, and for an `os.exec*` of this interpreter by carrying the exec out with a completed environment; locked mode does the same for an explicit environment that merely lacks the variable, and refuses one that carries another value and a process environment that lost it). Under a lock, an inherited environment is also compared with the variable as the process itself holds it, because `os.environ` is one interpreter's copy and shows neither another interpreter's change nor one made below Python. A Python interpreter runs `tethered._autoactivate` on startup when `tethered.pth` is in a site directory it processes — site-packages or the enabled user site, not an editable install's `src/`. The child re-engages tethered with the parent's policy before user code runs. The file counts as the bootstrap only while it holds tethered's own line, which is checked at `activate()` and again at each launch of a Python child (`_is_bootstrap_file`). The same bootstrap is how a subinterpreter of a locked process joins the lock (decision 7): the variable has to be present for the bootstrap to run, but the policy that is joined comes from the guardian, not from the variable. This covers `multiprocessing.Pool`, `ProcessPoolExecutor`, gunicorn/uvicorn workers, and plain `subprocess.run([sys.executable, ...])`. A worker that inherits an enforcing policy cannot load uvloop (decision 10), so a server that prefers uvloop runs such a worker on the standard loop; a worker that inherits a log-only policy can, and the audit hook then sees nothing that goes through its event loop, launches through `asyncio.create_subprocess_exec` included (see "Event loops" under Documentation). A policy reaches a process when it starts: workers that existed before `activate()`, and every worker of a multiprocessing fork server that was started before it, hold none. `external_subprocess_policy` (`warn`/`block`/`allow`, default `warn`) controls parent-side enforcement for launches that auto-inherit can't reach: non-Python tools, different Python interpreters, `sys.executable` with `-S` (the only site-bypass flag; `-s` and `-I` count only when the hook is in the per-user site-packages, and `-E` never does), a POSIX launch whose `argv[0]` is not `sys.executable`, interpreter options that cannot be parsed, any Python launch when no processed `tethered.pth` exists, a Python launch whose environment cannot be given the payload, and every launch where `sys.executable` is a program that embeds Python and not an interpreter (uWSGI without `--py-sys-executable`).

9. **Scope-to-subprocess propagation via frame-locals mutation.** `tethered.scope()` propagates to spawn-mode child processes: a child launched from inside `with scope(allow=[...])` inherits the parent's effective policy at the launch site (global ∩ scopes), not just the at-rest global. Implemented by mutating `subprocess.Popen._execute_child`'s `env` local from inside the `subprocess.Popen` audit hook (PEP 667 write-through proxy on 3.13+; `ctypes.pythonapi.PyFrame_LocalsToFast` on 3.11–3.12). The same mechanism injects the global payload when an explicit `env=` lacks it, with or without a scope. Race-free across threads because frame locals are per-call, not shared global state. Audit hooks are read-only on `args`, so frame-locals mutation is the only mechanism that satisfies the no-monkey-patch and no-opt-in constraints. An `os.exec*` of this interpreter is the one other route: there the hook carries the exec out itself with the scope in the environment (`_exec_with_policy`), which covers gevent's `Popen`. Limitation: scope cannot propagate through `os.system` / `os.startfile` / `os.spawn*` / `os.posix_spawn` (no env channel to inject) or through spawn-mode `multiprocessing` workers (they never reach `_execute_child`); those launches still receive the at-rest global only.

10. **Refuse to run where nothing would be enforced.** Where tethered knows that a policy would silently not be applied, it does not put it in place: `activate()` raises when its audit hook cannot be installed, and when uvloop is loaded (a uvloop event loop raises no audit event for anything it does, and uvicorn picks it whenever it is installed). While an enforcing policy is active it keeps uvloop from being imported, and pycares too (with c-ares, hosts allowed by name are refused and forbidden names still reach the name server), so that the servers and clients that prefer them fall back to what the hook sees. A log-only policy refuses nothing, these included, and a `scope()` without a policy only warns. This guards a deployment against being unenforced without anyone noticing; it is not a barrier to code that is out to get around tethered, which can load any other extension that does its own networking. What a real server does with each refusal (falls back, does not start, restarts its workers without end, or swallows the exception) was measured in the container suites and is in `docs/COMPATIBILITY.md`; a change to this behaviour has to be run against them.

## Conventions

### Code style

- Use `from __future__ import annotations` in all modules.
- Private modules are prefixed with `_` (e.g., `_core.py`, `_policy.py`).
- Type hints on all public function signatures.
- No docstrings on private helpers unless the logic is non-obvious.
- Keep modules small and focused. If a module exceeds ~500 lines, consider splitting.

### Testing

- **Egress guard** (`conftest.py`): An independent audit hook that uses `AllowPolicy` to block unexpected network access between tests (when tethered is deactivated). Only `dns.google` and localhost are allowed. When tethered IS active, its own hook handles enforcement and the guard is a no-op. Because the guard raises `EgressBlocked` too, a test that expects a block from a scope should assert where it came from (e.g. `scope_label`). - **Autoactivate tests** (`test_autoactivate.py`): Direct unit tests for `_autoactivate_from_env()` (no env, malformed JSON, idempotency, locked-mode propagation, payload schema validation, children that refuse to start when a locked or fail-closed policy cannot be established) and end-to-end integration tests that spawn real Python subprocesses to verify the .pth bootstrap. Includes `TestInheritScopes` for scope chain inheritance. `TestJoinLocked` and `TestBootstrapUnderALock` cover `_core._join_locked()` and the bootstrap of an interpreter that starts under another interpreter's lock, in the main interpreter with a stand-in for the guardian: code that runs inside another interpreter is invisible to coverage. `TestBootstrapTakesItsTurn` covers the bootstrap waiting for an `activate()` / `deactivate()` under way elsewhere (the claim is held by another thread here): it waits and then establishes the policy, goes by what the process holds after the wait, goes by what it found at startup where it cannot wait, and does not take an error raised after the wait for a wait that failed.
- **Subinterpreter tests** (`test_subinterpreters.py`): real subinterpreters (skipped where the stdlib offers none), with their own GIL and with the shared one where the version has both. One that existed before the lock (`TestLockedPolicy`), where tethered was imported and so no extension loaded, keeps computing and is refused connections, lookups, launches and changes to the bootstrap files or the policy variable. One created under the lock (`TestJoinedInterpreter`) reaches what the policy allows and is refused the rest by its own policy, cannot switch tethered off or change the policy variable, has tampering detected in it without the owner being affected, joins only once, and follows the lock through an identical replacement, a different one, release and re-locking. Also covered: log-only locks, `InterpreterPoolExecutor` on 3.14+, the lock outliving the interpreter that took it, a join that fails, a process without `site`, the other strict startup failures, the activation claim between interpreters (`TestTakingTurns`: a wait with the GIL released, the same thread in another interpreter, a holder that is destroyed, a waiter refused at the door once a policy was locked, an interpreter created while a locked policy is being replaced), and concurrency (many interpreters joining at once, interpreters racing for the first lock of a process (each loading the extension in its own `activate()`), a lock taken amid the unlocked transitions of other interpreters; the last two assert that the lock holder finds its own payload in the variable and that everyone else gets `TetheredLocked`). The wording `activate()` / `deactivate()` use in an interpreter outside the lock is asserted in full (`ACTIVATE_LOCKED` / `DEACTIVATE_LOCKED`, in `TestTakingTurns` and `TestConcurrency`), and `TestInterpretersSharingTheGil` checks that `holds_lock()` is false in an interpreter that did not take the lock. Tests whose lock can never be released, or in which a failure would end or hang the process, run in child processes. Every subinterpreter a test creates is destroyed.
- **Guardian tests** (`test_guardian.py`): C extension tamper detection. Replaces `_config`, monkey-patches `is_allowed`, mutates frozen dataclass slots via `object.__setattr__`, replaces helper functions (e.g., `_inject_scope_env`, `_find_execute_child_frame`) — all should fail-closed. `TestSnapshotCoverage` enumerates the globals of `_core` and `_policy` and fails for any name that is neither pinned nor on an explicit allowlist of runtime-state names, so a new module-level name must be one or the other. Also covers the guarded non-socket events, real operations on the hook file by another name of its directory, through the name uv keeps in its cache, attempts to give it a second name, and `shutil.rmtree` of that directory under a real lock (`TestPthGuardByAnotherName`), the hook's content under a lock (`TestHookContentUnderALock`: a read that is refused once the policy was tampered with, a hook emptied, or given a `tethered.start`, by another process, after which a locked policy launches no Python child under any `external_subprocess_policy`), replaced Python-side guards, the resolver window, the token being held only in C and not handed to the garbage collector, `holds_lock()` in the interpreter that takes and releases a lock, `join()` being refused to the owner, `locked_payload()`, several instances of the extension module in one interpreter, and an owner that has let go of every instance.
- **Cookbook recipes** (`test_docs_recipes.py`): the container suites hold copies of the recipes of `docs/COOKBOOK.md` between two marker lines (`# --- docs/COOKBOOK.md: begin ---` / `end`) and run them under real servers; this test fails when a copy and the code block it was taken from differ by a character, so a recipe cannot be changed in one place only. A copy inside a function is compared after dedenting. Skipped where `docs/` or `tests_containers/` is not part of the source copy.
- **Documentation site** (`test_docs_site.py`): the footer of the site names the version it describes, in the `copyright` line of `zensical.toml`, which `cz bump` rewrites with the other version fields; this test fails when that line and `tethered.__version__` differ. A second test fails when the site's share image (`docs/assets/social-preview.png`) is not the social preview byte for byte, or the template (`overrides/main.html`) names another file. Skipped where `zensical.toml` is not part of the source copy.

It reads the front matter with PyYAML, which is in the dev dependency group for that. Skipped where `zensical.toml` is not part of the source copy.
- **Changelog and citation file** (`test_changelog.py`): one test fails when a version of `CHANGELOG.md` has no compare link, when the links are not in the order of the sections, and when a link does not start at the version before; the second when `CITATION.cff` names another version than the package has, or another day for it than the heading of that version in the changelog; the third when the version of the distribution or commitizen's in `pyproject.toml` is not `tethered.__version__`, which no build compares them with. Skipped where the two files are not part of the source copy.
- **Preflight check** (`test_check.py`): `python -m tethered check`. Each finding appears when its condition holds and not otherwise, from a `Stage` in which the check finds nothing and a test changes one thing: stand-in distributions (`_check._distributions`), importable modules (`_check._importable`), bootstrap candidates in `tmp_path` (`_core._pth_candidates`), the module constants for the platform and `_core._SYS_EXECUTABLE_IS_PYTHON`. Also covered: the report and its width, the command line and its exit status (in-process, through `runpy`, and as a real `python -m tethered check`), and every link a finding prints, against the anchors of the headings of `docs/` (skipped where `docs/` is not part of the source copy). `TestItChangesNothing` runs the command in a child process with an audit hook installed first, and fake distributions and modules on `PYTHONPATH` whose import fails the run: no socket, launch, write or `sys.addaudithook` event, no third-party module imported, tethered's hook not live, no config, the guardian inactive, the policy variable absent. `TestTheShippedRowsAreTheCatalogues` loads `tests_containers/suites/clients/catalog.py` by its path and fails when `_clients.ROWS` is not exactly its rows that are not enforced, with the same title, result, packages and mechanism, in the same order (skipped where `tests_containers/` is not part of the source copy); a further test asserts that `_check` reports every shipped row exactly once.

- **Container suites** (`tests_containers/`): real servers, task queues and client libraries in Docker, on every supported Python version, with tethered installed from a wheel the way a user installs it. The unit and integration tests drive tethered from inside one pytest process; these start what people deploy (uvicorn, gunicorn and its worker classes, hypercorn, granian, sanic, aiohttp, daphne, tornado, Quart, FastAPI, uWSGI, waitress, mod_wsgi under Apache, Flask, Django, Celery, RQ, Dramatiq, Huey, arq, the standard library's pools, supervisord, some seventy client-library arrangements), let them fork, spawn, recycle and reload, and check from the outside that the policy holds in every process. The container has no network; a "world" on its loopback interface counts every connection and datagram that arrives, and those counters are the ground truth: a test asserts what the application reported and what arrived. A test whose docstring starts with `Limit:` pins a known limit as what happens today. The pytest process never holds a policy. A suite is a directory under `suites/` (a `suite.toml`, a pinned `requirements.txt`, `test_*.py`); nothing else has to be edited to add one. They are not collected by `uv run pytest tests/`, are not part of the coverage figure, and cannot run outside their containers. `tests_containers/AGENTS.md` is the reference.
- **The gating rule.** Run the container suites before merging a change to `src/tethered/_core.py`, `src/tethered/_autoactivate.py`, `src/tethered/_guardian.c`, `src/tethered.pth` or `setup.py`. CI runs them on every pull request that touches `src/`, `setup.py`, `pyproject.toml` or `tests_containers/` (`.github/workflows/container-tests.yml`), and weekly with `--unpinned` against the latest release of a week ago of every requirement, on one Python version (the one `.python-version` names). `docs/COMPATIBILITY.md` is written from these suites: when a suite's result changes, change the page with it, and when a new version changes what tethered has to do, write that down where the behaviour is documented before changing the test.
- **Parallel runs.** `tests/` runs under pytest-xdist. CI passes `-n auto`, one worker per CPU of its runner; the commands below pass `-n 8`, beyond which the run gets no shorter and only takes more memory. Each worker is a Python process of its own, with its own audit hooks, tethered state and C guardian, so the per-test cleanup is the same as in one process. What the workers share is the file system. A test writes below `tmp_path` and nowhere else, binds port 0, and does not rely on another test having run before it in the same process: xdist hands the tests of one file to several workers. A module-scoped fixture is built once in every worker that runs a test using it. What has to be in site-packages for the whole run is put there by the hooks in `conftest.py`, never by a fixture. A worker is not a single-threaded process (a second thread reads what the process that started it sends, and `threading.enumerate()` does not list it), so a test that forks the pytest process carries a `filterwarnings` mark for the warning Python gives from 3.12 about forking with threads, as the two fork-mode tests in `test_subprocess.py` do. `-n` is deliberately not in `addopts`: without it the tests run in one process, which is what a debugger and `-s` need.
- Run core tests: `uv run pytest tests/ -n 8`
- Run with coverage: `uv run pytest tests/ -n 8 --cov`
- Run example tests (requires network): `uv run pytest tests_examples/ -v`
- Run the container suites (requires Docker): `uv run python tests_containers/run.py` for everything, `--suite uvicorn --python 3.13` for one run, `-k EXPR` for pytest's filter, `--verbose` for the output of passing runs, `--list` for the suites
- **Example tests** (`tests_examples/test_examples.py`): Run each `examples/*.py` as a subprocess. They make real HTTP calls to `api.github.com`. Not included in coverage (subprocesses aren't measured). Kept in a separate directory to avoid affecting coverage thresholds. `tests_examples/conftest.py` copies `tethered.pth` into site-packages for the run, with the same two hooks as `tests/conftest.py`: without the hook in a site directory, examples 11 and 12 would have their own Python children treated as external.
- **Adding a new example**: when adding `examples/<NN>_*.py`, register it in `EXAMPLE_SCRIPTS` in `tests_examples/test_examples.py`. The list is intentionally explicit (not a glob) so draft scripts don't enter the test rotation. Each registered example must exit with code 0 on the happy path, produce stdout, and print the literal token `(unexpected)` on any branch that should have been blocked by tethered — the test asserts `(unexpected)` is NOT present, so a tethered regression that allows a blocked call surfaces immediately.
- Core tests that need DNS resolution (log-only, fail-open, IP map tests) are marked `@requires_network` and skip automatically if DNS is unavailable. The majority of core tests run fully offline.
- **Microbenchmark** (`benchmarks/overhead.py`): Standalone, zero-dep script measuring per-event wall-clock overhead — `socket.connect` (TCP, against a daemon-thread accept-and-close listener on 127.0.0.1), `socket.getaddrinfo`, `sys.audit` synthetic event, and `with tethered.scope(...)` enter+exit — across deactivated / activated / activated+scope / activated+locked. Run with `uv run python benchmarks/overhead.py` (default 5k per-event iterations, 3k TCP iterations with a median-of-3 to reject load-spike outliers on Windows where the connect baseline is ~700 µs vs ~30 µs on Linux) or `--iterations N`. Not part of the test suite; intended for ad-hoc measurement.
- **DNS benchmark** (`benchmarks/dns_lookups.py`): what tethered's own lookup of an allowed name costs against real resolvers, which `overhead.py` cannot show (it looks up `localhost`). It needs Docker and nothing on the host beyond the standard library: it builds an image from `benchmarks/dns_lookups/Dockerfile` (tethered as a wheel built from the working tree, installed into `python:X.Y-slim`, as `tests_containers/images/base.Dockerfile` does it; systemd-resolved, dnsmasq and gevent besides), runs it with `--network none --cap-add NET_ADMIN`, and prints Markdown tables. Inside, `upstream.py` is a DNS server written with the standard library that answers a test zone after a fixed latency (20 ms by default) and counts the queries it receives; `inside.py` gives the container a dummy interface (systemd-resolved forwards nothing without a non-loopback link that is up, and caches nothing from a server on a loopback address, so the upstream listens on that interface), rewrites `/etc/resolv.conf` for each setup (no cache, gevent's default resolver, systemd-resolved run without systemd, dnsmasq), and runs every measurement in a fresh `probe.py` process with a freshly started stub; the probe waits on a handshake so that the driver reads the upstream's counters from outside the process, where tethered does not see them. Three measurements: `getaddrinfo` deactivated, activated and locked (one name, and a new name each call); a connect to an address that no name is known for after 30 allowed names were looked up (the fallback search, deactivated, log-only and enforcing; under gevent with the longest stall of the hub); and the share of connections refused for a load-balanced name whose answers are a random subset of a pool (`lb-K-of-P[-ttl-T].bench.test`, addresses in 198.18.0.0/15), as the first connection of a process and over one process. `--host-name NAME` adds this machine's own resolver with a real name. Run with `uv run python benchmarks/dns_lookups.py` (about a quarter of an hour; `--only`, `--iterations`, `--trials`, `--latency-ms`, `--python`, `--cpuset-cpus`, `--json`). Not part of the test suite or of CI; `docs/ARCHITECTURE.md` (`## Performance`) and `docs/security.md` ("Known residual DNS divergence") quote its results.

- Ruff handles linting and formatting. Configuration is in `pyproject.toml` under `[tool.ruff]`.
- Bandit handles security scanning. Configuration is in `pyproject.toml` under `[tool.bandit]`. Tests are excluded. Intentional suppressions use inline `# nosec BXXX` comments.
- Interrogate enforces docstring coverage on public items in `src/`. Configuration is in `pyproject.toml` under `[tool.interrogate]`. Private/magic/init are excluded (consistent with the "no docstrings on private helpers" convention). `fail-under = 100`.
- Deptry compares what the code imports with what `pyproject.toml` declares. Configuration is in `pyproject.toml` under `[tool.deptry]`. The package declares no dependency, so an import of anything outside the standard library in `src/` fails the check; the two dev dependencies that are imported outside the tests (`httpx` in `examples/`, `invoke` in `tasks.py`) are named there. `benchmarks/dns_lookups/` is left out (`extend_exclude`): it runs inside the DNS benchmark's image, which installs what it imports (gevent), as `tests_containers/` is left out by deptry's default exclusion of `tests`.
- Licenseal checks the licences of what tethered depends on against tethered's own. It runs in CI, in a workflow of its own (`.github/workflows/licenseal.yml`), and is not a pre-commit hook; the check asks the package registry for each dependency. It scans the package's own dependencies and not the dev group (no `--dev`), which is not distributed with tethered. tethered has none, so the check passes with nothing to judge. `tests_containers/` and `benchmarks/dns_lookups/` are left out (`--exclude-dirs`): their `requirements.txt` files name what the container suites and the DNS benchmark install into their images, which tethered neither depends on nor ships. A new `requirements.txt` or other manifest elsewhere in the repository is read as a dependency of tethered: leave its directory out the same way.
- **A release counts only a week after its upload**, when a compromised one has been found and removed (a release of litellm that stole credentials was on PyPI for two hours on 2026-10-21). `[tool.uv] exclude-newer = "7 days"` in `pyproject.toml` keeps younger releases out of `uv.lock` and out of the build requirements of `uv build` and `uv sync`, and `uv pip compile` takes it when it runs at the root of the repository, which is how `.github/docs-constraints.txt` is written (uvx, which installs from that file, does not read the setting). `min-release-age=7` in `.npmrc` does the same for `package-lock.json`. pip does not read `[tool.uv]`, so the publish workflow gives cibuildwheel and the sdist round trip `PIP_UPLOADED_PRIOR_TO=P7D` (pip 26.1 or later; cibuildwheel 4.3.3 and its manylinux and musllinux images carry 26.2.2): the published wheels and the sdist are built with the setuptools of a week ago. cibuildwheel installs its own pinned tools after it applies `CIBW_ENVIRONMENT`, so the cutoff holds them back too: a cibuildwheel release whose pins are younger than a week fails the wheel builds until they are a week old (4.3.3, taken early for the emSign CA compromise, until 2026-10-28 02:00 UTC). Rehearse a new one before a release: `uvx cibuildwheel==X.Y.Z --platform windows` at the root, with the workflow's `CIBW_*` settings in the environment. Never shorten the cooldown or work around it to take a release early. A security fix that is younger goes in by decision of the maintainer, through `[tool.uv] exclude-newer-package` with a date just after the upload of the fix, never `false`: once the week has passed the span admits the same and the entry would hold the package back, so the check below fails until it is removed (none today; the last was certifi 2026.10.19, for GHSA-6q48-6c7w-9gw2). The images of the container suites and of the DNS benchmark do the same for every pip install, pinned or not, build requirements included (`ARG PIP_UPLOADED_PRIOR_TO=P7D`, with pip 26.2.2, installed by its URL with its hash, where the image's own pip is older: before 26.1 pip ignores the variable, and before 26.2.2 it trusts the emSign CAs whose keys were compromised, through the CA bundle it carries): a pin younger than a week fails the image build, and `--unpinned` takes the latest releases of a week ago (`tests_containers/AGENTS.md`, "Pins").
- **`scripts/check_advisories.py`** (the `advisories` pre-commit hook) checks both settings and every `exclude-newer-package` entry, and asks [osv.dev](https://osv.dev) for the advisories of each version of `uv.lock`, `package-lock.json` and `.github/docs-constraints.txt`, and of the uv the workflows install (their `UV_VERSION`, as PyPI's `uv`: CI's uv 0.13.0 trusted the compromised emSign CAs, GHSA-hq85-5cpj-mr62). A known vulnerability or a report of a malicious package fails it, but for the advisories in its `ACCEPTED_ADVISORIES`, each with its reason and, where a fix is younger than the cooldown, the time the cooldown admits the fix, from which the check fails until the package is upgraded (tethered has no check of the latest versions that would say so; today: four advisories of markdownlint-cli2 0.23.3's dependencies, fixed in 0.24.0, admitted from 2026-10-28, one of virtualenv 21.14.11, fixed in 21.14.13, admitted from 2026-10-29, and one that no release in range fixes); an accepted advisory that no version has fails it too, and a report of a malicious package (`MAL-`) is never accepted. The pins of the images (`tests_containers/`, `benchmarks/dns_lookups/`) are checked for reports of malicious packages only: they are installed with a network and run in containers without one. It runs at each commit, as an advisory can come out between two commits, so it can fail on a change that touches no dependency: say so, and upgrade past the advisory, or, where no version that the ranges admit fixes it, accept it with the reason; otherwise run the other hooks with `SKIP=advisories`. CI skips it (`SKIP: advisories` in the lint job), where its result would depend on the day and not on the commit. On a malicious package, tell the maintainer at once: each machine that installed it is compromised.

- What every workflow observes. GitHub Actions are pinned by commit SHA, with the version in a comment. A workflow that installs uv names the version in `UV_VERSION`, the same one in each: change them together. A workflow starts from `permissions: { contents: read }`, and a job that needs more names its own (CodeQL, the Pages deployment, the PyPI upload); a job's `permissions` replace the workflow's, so one that checks the repository out names `contents: read` again. Every `actions/checkout` sets `persist-credentials: false`: no job fetches or pushes after its checkout, and the token would otherwise stay in the workspace's git configuration for every later step to read (the tests, the hooks, the image builds of a pull request). A value of the event reaches a `run:` script through `env:`, never as `${{ }}` inside the script, where the shell would read it as code. Every job has a `timeout-minutes`.

### What NOT to do

- Do not add runtime dependencies. This library must remain zero-dep. The C extension uses the CPython C API, the C standard library and a few operating-system calls (no external C libraries).
- Do not monkey-patch `socket.socket` or any other stdlib class. The audit hook API is the only interception mechanism.
- Do not catch `EgressBlocked` inside tethered itself (except in tests). It must propagate to the caller.
- Do not add framework-specific code (Django, Flask, etc.) to the core package. Framework integrations belong in documentation, not code.
- Do not add features speculatively. Every addition must serve a concrete, current use case.
- Do not stage or commit changes. The developer reviews and commits manually.

### Adding new allow rule types

If adding a new rule type (e.g., regex patterns, deny lists):

1. Add a new `_XxxRule` `NamedTuple` in `_policy.py` with primitive fields only (strings and integers), plus a plain-tuple fields slot on `AllowPolicy` that the matching methods read. Rules must stay deeply immutable: the locked-mode guardian pins the identity of each policy slot, not what is reachable through it.
2. Parse it in `AllowPolicy.__init__`, appending exactly one parsed rule per allow-list entry to `parsed_rules`: the scope overlap warnings pair `_parsed_rules` with the allow list by position.
3. Check it in `is_allowed()` or `_check_hostname()`/`_check_ip()`.
4. Serialize it in `_serialize_allow_list()` (`_core.py`) so that child processes rebuild the same rule; the serialized form must re-parse to an identical policy.
5. Classify it in `AllowPolicy._check_rule_overlap()`, so that `scope()` overlap warnings understand the new kind. Return "unknown" for whatever cannot be decided for certain; a guess would be logged as a fact.
6. Add unit tests in `test_policy.py` first, then integration tests if needed.

### Adding a mechanism

A mechanism is a way for tethered to reach into the process beyond deciding at the audit events it already handles: handling another audit event, writing into another function's frame, carrying out a call for the caller, recognising code by its code object or a private name, reading state below Python, refusing an import. Each one relies on something CPython or a library does not promise, runs in the process of an application, and breaks in its own way when what it relies on changes.

1. Add one only for a failure reproduced in a setup tethered supports (a server, task queue, client library or installer, on any supported platform), with a test that fails without it: in `tests/`, or in a container suite where the setup needs one. A path found by reading the code is not such a failure.
2. Switch it on only where that setup is present, as `_warn_if_uvloop` looks in `sys.modules` and never imports, so that other processes do not carry it.
3. Record it in the inventory in `docs/ARCHITECTURE.md` ("What tethered relies on"): what it relies on, the setup that needs it, and the test that pins it.
4. A wrong decision inside an existing check (an address form that is not checked, a launch classified wrongly) is a fix, not a mechanism: fix it with a unit test, as before.
5. An attack by code written against tethered is answered in `docs/security.md`, which states what locked mode does and does not do. Widening that promise is a decision about the promise, taken as such, not a mechanism added for one attack.
6. The mechanisms already there are held to the same bar. Removing one that closes a hole weakens security against the last release: it needs its own case, and an entry under Breaking changes or Security in the changelog.

### Python version support

- Python 3.11–3.15. `sys.addaudithook` was added in 3.8, so this is well within range.
- The bootstrap is an `import` line in `tethered.pth`. PEP 829 (Python 3.15) deprecates such lines in favour of `<name>.start` entry-point files. `site.py` runs them on 3.15–3.17 unless a `<name>.start` file lies beside the `.pth`, whatever it holds (one that is hidden, cannot be read or is not UTF-8 does not count); 3.18 is to ignore them, and 3.20 to warn about them. tethered ships no `tethered.start`; locked mode refuses creating one, and one that is there all the same is found at `activate()` and at each launch of a Python child. `test_cpython_ignores_a_pth_import_line_beside_a_start_file` in `tests/test_guardian.py` and `TestSiteStartup` in `tests/test_cpython_internals.py` pin that behaviour and will fail on 3.18, and so will every test of auto-activation: the `next-python.yml` job shows it from 3.18's first alpha once it runs on 3.18.
- The move to a `tethered.start` bootstrap, which has to be in the release that adds Python 3.18, built and tested against 3.18's pre-releases:
  1. Keep the `.pth` line for Python 3.11–3.17 and ship `tethered.start` for 3.18 and later only. The line costs nothing measurable at startup. A `.start` entry point makes `site.py` import `pkgutil` and what that imports (about 30 modules) at every interpreter start, a policy or not: measured with Python 3.15.0 and `python -c pass`, 6.4 ms became 11.0 ms on Linux and 36.8 ms became 45.2 ms on Windows.
  2. The entry point is a top-level module of its own, `src/_tethered_start.py`, beside the hook, and `tethered.start` holds the one line `_tethered_start:main` (`pkgutil.resolve_name(..., strict=True)` takes only the `module:callable` form). `main()` does what the `.pth` line does, `import tethered._autoactivate` when `_TETHERED_CHILD_POLICY` is in `os.environ`, and the module imports nothing but `os`. Not an entry point inside the package: that imports `tethered` and `tethered._core` at every interpreter start (about 74 modules and 34 ms on Windows with 3.15). `site.py` runs entry points after the `.pth` import lines and before `import sitecustomize`, and lets `SystemExit` out of them (`except Exception`), so the fail-closed start of a child and the guardian's startup window keep working; `TestSiteStartup` pins both on 3.15+. `main()` can also do what the `.pth` line cannot: raise `SystemExit` when the import of `tethered._autoactivate` fails and the variable asks for `locked` or `fail_closed` (a removed package, a pip stopped halfway).
  3. The wheels: `setup.py`'s `build_py_with_pth` puts `tethered.start` and `_tethered_start.py` beside the hook, in place of `tethered.pth`, when the interpreter that builds is 3.18 or later. cibuildwheel builds each wheel with an interpreter of its version, and an sdist is built by the interpreter it is installed for, so every wheel up to cp317 keeps today's layout. `scripts/wheel_smoke_test.py` checks the files of the version it runs on and that a child auto-activates through them. The new module is in `src/`, so ruff, ty, bandit, interrogate (a docstring for `main`) and deptry check it.
  4. `_core` decides by one constant which file is the hook, `_HOOK_IS_START_FILE = sys.version_info >= (3, 18)`, which tests flip as they flip `_START_FILE_SILENCES_PTH`. Where it is true: `_is_bootstrap_file` checks `tethered.start` against a constant `_START_BOOTSTRAP` and `_tethered_start.py` against the module's full text (a test compares both constants with `src/`, as one does `_PTH_BOOTSTRAP` today); `_pth_candidates` and `_compute_pth_path` find the `tethered.start` of the first site directory that holds both files, `_Config._pth_path` holds its path and the module's is derived from it; `_launch_exclusion` reads both files at each launch, and `_HOOK_CHANGED_REASON`, `_stand_in_pth_path` and the warnings of `activate()` name them; `_start_file_beside`, `_silenced_pth_path` and `_HOOK_SILENCED_REASON` apply only where the constant is false (3.15–3.17).
  5. The locked-mode guard (`_handle_pth_fs_op`, `_path_matches_pth`, `_gives_pth_another_name`) guards `tethered.start` and `_tethered_start.py` as it guards `tethered.pth` today, and no longer refuses creating a `tethered.start` where that is the hook. Its two pre-filters learn a third name: `_mentions_hook` looks for `"tethered."`, which the path of `_tethered_start.py` does not hold, and so does `path_mentions_pth` in `_guardian.c`. The event lists (`_PTH_FS_EVENTS`, `classify_event`) stay as they are. `docs/security.md` names the guarded files, and its limits apply to both.
  6. The tests run on both sides of the constant: `TestBootstrapFile`, `TestStartFileBesideTheHook`, `TestComputePthPath`, `TestPthFsHook`, `TestPthGuardByAnotherName`, `TestAnInstalledHookThatIsNotTethereds` (which installs the files of the running version into its scratch venv), `TestStartFileGuard` and `TestHookContentUnderALock`; `conftest.py`'s `pytest_configure` installs the files of the running version into site-packages, and `tests_examples/conftest.py` with it. `test_cpython_ignores_a_pth_import_line_beside_a_start_file` expects the line ignored from 3.18, with a `.start` beside it or not. The container suites need nothing: they install a wheel.
  7. A mixed installation: one site directory holds the files of one tethered, which an upgrade or a downgrade replaces as its record says. A `tethered.pth` left behind beside a 3.18 hook is ignored by `site.py` and by tethered. A `tethered.start` whose module or package is gone makes `site.py` print the failed import at every interpreter start and go on; the launch check takes the hook for lost, as it takes an emptied `tethered.pth` today. A process that still runs the earlier tethered after the upgrade no longer finds its hook, and under a lock refuses Python children until it is restarted, as after any upgrade that changes the hook. Interpreters of different versions share no site directory (site-packages and the user site are per version), and a directory on `PYTHONPATH` is not a site directory under either layout.
  8. Then the docs: `docs/security.md` and `docs/SUBPROCESS.md` say which file is the bootstrap on which version, the inventory in `docs/ARCHITECTURE.md` gets an entry for the entry point (what `site.py` does with it, pinned by `TestSiteStartup`), the README and `PYPI.md` where they name `tethered.pth`, and this file (Architecture, Key design decision 8).
- Do not use syntax or features unavailable in 3.11 (e.g., no `type` statement from 3.12).
- `.python-version` names the development interpreter, 3.14, and says nothing about what tethered supports (that is `requires-python`). A plain `uv sync` or `uv run` in a checkout builds the project environment on it, so the pre-commit hooks run on it too, and the CI jobs outside the test matrix install it with a bare `uv python install` (lint, CodeQL, the sdist build, and the docs build, where `uvx` does not read the file and takes that Python as the only one uv has installed). uv holds the project environment to the file: a `uv run` in an environment built on another version removes it and builds it again on 3.14, whatever `uv sync --python X.Y` was told before. The test job of `ci.yml` therefore sets `UV_PYTHON` to the version of its cell, which outranks the file, and a step fails the cell when `uv run` is on another Python; without the variable every cell would test 3.14 and pass. Keep both when that job changes. The steps of that job that update the coverage badge run in one cell, the one on the development interpreter, and name its version in their condition: change it with the file. To run on another version locally, use `uv run --isolated --python X.Y pytest tests/`, which leaves the project environment alone, or an environment of its own (`UV_PROJECT_ENVIRONMENT`) with `UV_PYTHON=X.Y` set for every uv command; `uv run --no-sync` uses an environment as it is and only warns. The container suites and cibuildwheel are not affected by the file: an image, or an interpreter, of the version under test does the build. One thing does read it: the weekly run of the container suites takes the one Python version it runs on from the file (`container-tests.yml` passes it to `run.py --python`), so the file has to name a version that `PYTHON_IMAGE_TAGS` in `tests_containers/run.py` knows, as `X.Y`.
