# Architecture — how tethered works

[← Back to README](../README.md)

tethered uses [`sys.addaudithook`](https://docs.python.org/3/library/sys.html#sys.addaudithook) (PEP 578) to intercept socket operations at the interpreter level:

- **`socket.getaddrinfo`** — blocks DNS resolution for disallowed hostnames and records IP-to-hostname mappings for allowed hosts.
- **`socket.gethostbyname` / `socket.gethostbyaddr`** — intercept alternative DNS resolution paths, including reverse-DNS lookups of raw IPs. An allowed `gethostbyname` (the event `gethostbyname_ex` raises too) records the name as a fallback candidate, so that a later connect to the address it returned can be matched back to the name. `socket.getnameinfo` is not checked: its audit event carries the address but not the flags, so a reverse lookup cannot be told apart from numeric formatting.
- **`socket.connect`** (including `connect_ex`, which raises the `socket.connect` audit event in CPython) — enforces the allow list on TCP connections.
- **`socket.sendto` / `socket.sendmsg`** — enforces the allow list on UDP datagrams.
- **`socket.__new__`** — no enforcement. On Windows it is used to log a one-time warning when a socket is created while an asyncio `ProactorEventLoop` is running (see below).

When `getaddrinfo` resolves a hostname, tethered records the IP-to-hostname mapping in a bounded LRU cache: up to 4096 addresses, keyed by the canonical text of the address (IPv6 compressed and without scope ID, IPv4-mapped IPv6 as the IPv4 address), each with up to 8 hostnames, most recent first. When a subsequent `connect()` targets that IP, tethered looks up the hostnames and checks them, and the raw IP, against the allow list; the connection is allowed if any of them is. If denied, `EgressBlocked` is raised before the connection is attempted. One caveat: CPython resolves a hostname passed directly to `connect()` / `sendto()` before it raises the audit event, so that lookup has already happened when tethered refuses the call.

Addresses are read in every form CPython accepts: `str`, `bytes` or `bytearray` hosts, and any port object with `__index__`. An address on an IP-family socket that tethered cannot read is refused.

## DNS-divergence fallback

The audit-hook architecture has an inherent limitation: tethered's resolution (called from inside the `socket.getaddrinfo` audit hook) and CPython's own resolution (whose result is returned to the application) are **two independent DNS queries**. For load-balanced services with short TTLs, and especially under gevent's threadpool resolver, the two queries can return different IP sets — leaving the connect-time IP unmapped. Eager population can never be perfect within the audit API.

When `_handle_connect` sees an unmapped IP, `_fallback_resolve` re-resolves up to 30 most-recently-allowed hostnames (LRU order, newest first) and checks if any maps to the connecting IP. On a hit it returns the hostname and enriches the IP map so future connects to that IP take the fast path. On a miss it returns `None` and the connect-time policy check then sees the bare IP, which doesn't match any hostname allow rule, and blocks. Hot path (mapped IP) is unaffected — the fallback fires only on misses, and it is skipped when every layer already allows the raw IP (loopback, an IP or CIDR rule), because no hostname could change that outcome.

Candidates are recorded after the scope checks, so only names whose lookup the global policy and every enforcing scope let through are ever re-resolved. `gethostbyname` lookups record a candidate too, but no mapping; the fallback is how an address obtained that way is matched to its name.

In locked mode, `_fallback_resolve` is the second authorized caller of `_c_guardian.resolve` (slot 1 in the C guardian's `expected_caller_codes` array; slot 0 is `_handle_getaddrinfo`). Like every function in the module it is covered by the C guardian's integrity snapshot, so replacing it with a no-op that defeats the divergence repair is detected. The resolver that `_c_guardian.resolve` calls is the `_socket.getaddrinfo` captured when the policy was locked. Inside the resolution only the resolver's own `socket.getaddrinfo` event is exempt from the guardian's checks; a `connect`, `sendto` or `sendmsg` event raised from inside it is refused.

This works with libraries built on CPython sockets (requests, httpx, urllib3, aiohttp) and frameworks like Django, Flask, and FastAPI — they all call `socket.getaddrinfo` and `socket.connect` under the hood. Asyncio and async libraries using CPython sockets are supported on selector event loops: the socket calls they make raise the same audit events, so `asyncio`, `aiohttp`, and `httpx` async go through the same connect-time checks as synchronous code. Two things differ. `loop.getaddrinfo` runs `socket.getaddrinfo` in an executor thread, where the global policy applies and the caller's scopes are not visible; so that the connect can still be matched to the name, a lookup made in a context with no policy and no scope is recorded while any scope is active in the process. And on Windows the default `ProactorEventLoop` connects and sends through `_overlapped` calls that raise no `socket.connect` / `socket.sendto` event, so there is no connect-time enforcement on that loop; tethered logs a one-time warning, and `asyncio.SelectorEventLoop` is the supported loop.

`scope()` uses `contextvars.ContextVar` to push a per-context policy onto a stack. The audit hook checks the context-local scope stack in addition to the global policy. When a scope is active, a connection must pass both the global policy and every scope on the stack. When the context manager exits (or the decorated function returns), the scope's own entry is removed from the stack, by identity, so exits that happen out of order do not disturb other scopes. A generator suspended inside a `with scope():` block leaves that scope on the consumer's stack until it resumes. Because `ContextVar` is async-safe, scopes propagate correctly through `await` chains and `asyncio.create_task()`. Scopes do **not** automatically propagate to child threads — use `scope()` at the I/O point inside the thread, or use `activate()` for a process-wide ceiling.

The per-connection overhead is a Python function call with hostname normalization, a dictionary lookup, and pattern matching — designed to add minimal overhead relative to actual network I/O.

## Subprocess audit handling

In addition to socket events, the audit hook also intercepts process launches (`subprocess.Popen`, `os.system`, `os.exec*`, `os.posix_spawn`, `os.spawn*`, `os.startfile`, and the two events raised by launches that bypass `subprocess.Popen`, such as `multiprocessing` workers: `_winapi.CreateProcess` on Windows and, from Python 3.14, `_posixsubprocess.fork_exec` on POSIX) for `external_subprocess_policy` enforcement, establishing the policy payload in the child's launch environment, locked-mode payload-integrity checks, and scope propagation to spawn-mode children. It also handles `os.putenv` / `os.unsetenv` for the policy variable, because `os.environ` does not show changes made through them. See [SUBPROCESS.md](SUBPROCESS.md) for the full mechanics.

In locked mode, the audit hook also intercepts filesystem events (`os.remove`, `os.rename`, `open` write-mode, `os.chmod`, `os.truncate`, and `_winapi.CopyFile2`, which `shutil.copy2` writes through on Windows) on the `tethered.pth` path to refuse Python-level tampering with the auto-propagation hook. That path is the hook found in a site directory this interpreter processes; it is empty when there is none, and then there is nothing to guard.

The same hook refuses creating a `tethered.start` file beside `tethered.pth` (a write-mode `open`, the destination of `os.rename`, `os.link`, `os.symlink` or `_winapi.CopyFile2`). The bootstrap is an `import` line in a `.pth` file, and PEP 829 changes how Python treats those: from Python 3.15, `site.py` ignores the `import` lines of `<name>.pth` when a `<name>.start` file sits beside it, whatever that file contains, and Python 3.18 is to ignore such lines altogether in favour of `.start` entry points. tethered ships no `tethered.start`; on Python 3.15–3.17 the `.pth` line runs as before.

## C guardian — tamper-resistant locked mode

When `activate(locked=True)` is called, a C extension (`_guardian.c`) records a list of facts that `_core` generates from the namespaces of `tethered._core` and `tethered._policy`: what every module-level name is bound to (except `_config`, which the guardian tracks itself, and lower-case scalar runtime state), every class attribute of the classes defined there, the `__code__` of every Python function found, that no builtin those modules use is shadowed in their namespaces, that no `__getattribute__` / `__getattr__` has been added to those classes, and the class and every slot of the active `_Config` and `AllowPolicy`. The guardian re-checks the list on every socket audit event, every process-launch event, and the filesystem and environment events above when they concern `tethered.pth`, `tethered.start` or the policy variable (those are pre-filtered in C, so ordinary `open` calls stay cheap). Any mismatch (object replaced, method monkey-patched, frozen field mutated via `object.__setattr__`, bytecode swapped) refuses the operation — `EgressBlocked` for socket events, `SubprocessBlocked` for the others — and a tamper alert is written to fd 2. What the snapshot does not cover is listed in [SECURITY.md](../SECURITY.md#locked-mode--what-it-does-and-does-not-do).

The C guardian also owns the lock state. It alone holds the token, `deactivate()` and `activate()` go through C for token verification, and it rebinds `_core._config` itself as part of its own commit, so no audit event sees a config and a snapshot that belong to different policies and swapping `_config` to an unlocked configuration doesn't help. A policy that fails the integrity check can be neither replaced nor deactivated. The lock is process-wide: for an event raised in any other interpreter the guardian reads only three atomics (active, owner, and the policy's `log_only` flag copied at commit) and the event's own arguments, never the owner's objects, and refuses the guarded operations there with an exception created in that interpreter; under a log-only lock it lets that interpreter's socket events pass. When the guardian adds its hook it confirms the hook is live with a private probe event (`tethered._guardian.probe`), and activation fails with `RuntimeError` if another audit hook refused it. `locked=True` requires the C extension; the extension is always built during installation, and a C compiler is required for source installs.

## Thread safety

`AllowPolicy` is deeply immutable after construction: rules are tuples of strings and integers, networks are stored as integers, and matching reads plain tuples, so no rule field can be reassigned in place. The `_Config` bundle is a frozen `dataclass` swapped by a single reference assignment; a hook reads `_config` once and works from that object. `activate()` and `deactivate()` are serialized from start to finish by a re-entrant lifecycle lock, so the config, the guardian state and the child-policy variable change together; `_state_lock` only guards the one-time installation of the audit hook. Installation is confirmed with the private audit event `tethered.hook_probe`, raised before adding (a hook that is already live is never added twice) and after (unanswered means another audit hook refused tethered's, and `activate()` / `scope()` raise `RuntimeError`). The IP-to-hostname map is an `OrderedDict` guarded by `_ip_map_lock` with LRU eviction. The process-wide count of active scope entries is guarded by its own lock. Reentrancy guard uses `contextvars.ContextVar` (async-safe, faster than `threading.local()`).

None of this has been validated on free-threaded Python (PEP 703). The C extension does not declare free-threaded support, so importing it on a free-threaded build re-enables the GIL, and no free-threaded wheels are published.
