# Architecture — how tethered works

[← Back to README](../README.md)

tethered uses [`sys.addaudithook`](https://docs.python.org/3/library/sys.html#sys.addaudithook) (PEP 578) to intercept socket operations at the interpreter level:

- **`socket.getaddrinfo`** — blocks DNS resolution for disallowed hostnames and records IP-to-hostname mappings for allowed hosts.
- **`socket.gethostbyname` / `socket.gethostbyaddr`** — intercept alternative DNS resolution paths, including reverse-DNS lookups of raw IPs. An allowed `gethostbyname` (the event `gethostbyname_ex` raises too) records the name as a fallback candidate, so that a later connect to the address it returned can be matched back to the name. `socket.getnameinfo` is not checked: its audit event carries the address but not the flags, so a reverse lookup cannot be told apart from numeric formatting.
- **`socket.connect`** (including `connect_ex`, which raises the `socket.connect` audit event in CPython) — enforces the allow list on TCP connections.
- **`socket.sendto` / `socket.sendmsg`** — enforces the allow list on UDP datagrams.
- **`socket.__new__`** — no enforcement. On Windows it is used to log a one-time warning when a socket is created while an asyncio `ProactorEventLoop` is running (see below).

When `getaddrinfo` resolves a hostname, tethered records the IP-to-hostname mapping in a bounded LRU cache: up to 4096 addresses, keyed by the canonical text of the address (IPv6 compressed and without scope ID, IPv4-mapped IPv6 as the IPv4 address), each with up to 8 hostnames, most recent first. When a subsequent `connect()` targets that IP, tethered looks up the hostnames and checks them, and the raw IP, against the allow list; the connection is allowed if any of them is. If denied, `EgressBlocked` is raised before the connection is attempted. One caveat: CPython resolves a hostname passed directly to `connect()` / `sendto()` before it raises the audit event, so that lookup has already happened when tethered refuses the call.

Addresses are read in every form CPython accepts: `str`, `bytes` or `bytearray` hosts, and any port object with `__index__`. An address on an IP-family socket that tethered cannot read is refused.

## DNS-divergence fallback

The audit-hook architecture has an inherent limitation: tethered's resolution (called from inside the `socket.getaddrinfo` audit hook) and CPython's own resolution (whose result is returned to the application) are **two independent DNS queries**. For load-balanced services with short TTLs, and especially under gevent's threadpool resolver, the two queries can return different IP sets — leaving the connect-time IP unmapped. Eager population can never be perfect within the audit API.

When `_handle_connect` sees an unmapped IP, `_fallback_resolve` re-resolves up to 30 most-recently-allowed hostnames (LRU order, newest first) and checks if any maps to the connecting IP. On a hit it returns the hostname and enriches the IP map so future connects to that IP take the fast path. On a miss it returns `None` and the connect-time policy check then sees the bare IP, which doesn't match any hostname allow rule, and blocks. Hot path (mapped IP) is unaffected — the fallback fires only on misses, and it is skipped when every layer already allows the raw IP (loopback, an IP or CIDR rule), because no hostname could change that outcome.

Candidates are recorded after the scope checks, so only names whose lookup the global policy and every enforcing scope let through are ever re-resolved. `gethostbyname` lookups record a candidate too, but no mapping; the fallback is how an address obtained that way is matched to its name.

In locked mode, `_fallback_resolve` is the second authorized caller of `_c_guardian.resolve` (slot 1 in the C guardian's `expected_caller_codes` array; slot 0 is `_handle_getaddrinfo`). Like every function in the module it is covered by the C guardian's integrity snapshot, so replacing it with a no-op that defeats the divergence repair is detected. The resolver that `_c_guardian.resolve` calls is the `_socket.getaddrinfo` captured when the policy was locked or, in an interpreter that joined the lock, its own `_socket.getaddrinfo` as it was when it joined. Inside the resolution only the resolver's own `socket.getaddrinfo` event is exempt from the guardian's checks; a `connect`, `sendto` or `sendmsg` event raised from inside it is refused.

This works with libraries built on CPython sockets (requests, httpx, urllib3, aiohttp) and frameworks like Django, Flask, and FastAPI — they all call `socket.getaddrinfo` and `socket.connect` under the hood. Asyncio and async libraries using CPython sockets are supported on selector event loops: the socket calls they make raise the same audit events, so `asyncio`, `aiohttp`, and `httpx` async go through the same connect-time checks as synchronous code. Two things differ. `loop.getaddrinfo` runs `socket.getaddrinfo` in an executor thread, where the global policy applies and the caller's scopes are not visible; so that the connect can still be matched to the name, a lookup made in a context with no policy and no scope is recorded while any scope is active in the process. And on Windows the default `ProactorEventLoop` connects and sends through `_overlapped` calls that raise no `socket.connect` / `socket.sendto` event, so there is no connect-time enforcement on that loop; tethered logs a one-time warning, and `asyncio.SelectorEventLoop` is the supported loop.

`scope()` uses `contextvars.ContextVar` to push a per-context policy onto a stack. The audit hook checks the context-local scope stack in addition to the global policy. When a scope is active, a connection must pass both the global policy and every scope on the stack. When the context manager exits (or the decorated function returns), the scope's own entry is removed from the stack, by identity, so exits that happen out of order do not disturb other scopes. A generator suspended inside a `with scope():` block leaves that scope on the consumer's stack until it resumes. Because `ContextVar` is async-safe, scopes propagate correctly through `await` chains and `asyncio.create_task()`. Scopes do **not** automatically propagate to child threads — use `scope()` at the I/O point inside the thread, or use `activate()` for a process-wide ceiling.

The per-connection overhead is a Python function call with hostname normalization, a dictionary lookup, and pattern matching — designed to add minimal overhead relative to actual network I/O.

## Subprocess audit handling

In addition to socket events, the audit hook also intercepts process launches (`subprocess.Popen`, `os.system`, `os.exec*`, `os.posix_spawn`, `os.spawn*`, `os.startfile`, and the two events raised by launches that bypass `subprocess.Popen`, such as `multiprocessing` workers: `_winapi.CreateProcess` on Windows and, from Python 3.14, `_posixsubprocess.fork_exec` on POSIX) for `external_subprocess_policy` enforcement, establishing the policy payload in the child's launch environment, locked-mode payload-integrity checks, and scope propagation to spawn-mode children. It also handles `os.putenv` / `os.unsetenv` for the policy variable, because `os.environ` does not show changes made through them. A change made from another interpreter or below Python shows up neither in `os.environ` nor in these events, so in locked mode a launch that inherits the environment also reads the variable from the process environment itself (see [The policy variable](#the-policy-variable)). See [SUBPROCESS.md](SUBPROCESS.md) for the full mechanics.

In locked mode, the audit hook also intercepts filesystem events (`os.remove`, `os.rename`, `open` write-mode, `os.chmod`, `os.truncate`, and `_winapi.CopyFile2`, which `shutil.copy2` writes through on Windows) on the `tethered.pth` path to refuse Python-level tampering with the auto-propagation hook. That path is the hook found in a site directory this interpreter processes; it is empty when there is none, and then there is nothing to guard.

The same hook refuses creating a `tethered.start` file beside `tethered.pth` (a write-mode `open`, the destination of `os.rename`, `os.link`, `os.symlink` or `_winapi.CopyFile2`). The bootstrap is an `import` line in a `.pth` file, and PEP 829 changes how Python treats those: from Python 3.15, `site.py` ignores the `import` lines of `<name>.pth` when a `<name>.start` file sits beside it, whatever that file contains, and Python 3.18 is to ignore such lines altogether in favour of `.start` entry points. tethered ships no `tethered.start`; on Python 3.15–3.17 the `.pth` line runs as before.

## C guardian — tamper-resistant locked mode

When `activate(locked=True)` is called, a C extension (`_guardian.c`) records a list of facts that `_core` generates from the namespaces of `tethered._core` and `tethered._policy`: what every module-level name is bound to (except `_config`, which the guardian tracks itself, and lower-case scalar runtime state), every class attribute of the classes defined there, the `__code__` of every Python function found, that no builtin those modules use is shadowed in their namespaces, that no `__getattribute__` / `__getattr__` has been added to those classes, and the class and every slot of the active `_Config` and `AllowPolicy`. The guardian re-checks the list on every socket audit event, every process-launch event, and the filesystem and environment events above when they concern `tethered.pth`, `tethered.start` or the policy variable (those are pre-filtered in C, so ordinary `open` calls stay cheap). Any mismatch (object replaced, method monkey-patched, frozen field mutated via `object.__setattr__`, bytecode swapped) refuses the operation — `EgressBlocked` for socket events, `SubprocessBlocked` for the others — and a tamper alert is written to fd 2. What the snapshot does not cover is listed in [SECURITY.md](../SECURITY.md#locked-mode--what-it-does-and-does-not-do).

The C guardian also owns the lock state. It alone holds the token, `deactivate()` and `activate()` go through C for token verification, and it rebinds `_core._config` itself as part of its own commit, so no audit event sees a config and a snapshot that belong to different policies and swapping `_config` to an unlocked configuration doesn't help. A policy that fails the integrity check can be neither replaced nor deactivated. The token is not reported to the garbage collector, so `gc.get_referents()` does not hand it out. When the guardian adds its hook it confirms the hook is live with a private probe event (`tethered._guardian.probe`), and activation fails with `RuntimeError` if another audit hook refused it. `locked=True` requires the C extension; the extension is always built during installation, and a C compiler is required for source installs.

### Interpreters

A process can hold several interpreters, and the two hooks see them differently. tethered's Python hook is added with `sys.addaudithook` and belongs to one interpreter: each interpreter has its own `tethered._core`, its own `_config` and its own hook. The guardian's hook is added with `PySys_AddAuditHook` and is called for the events of every interpreter in the process. So there is one lock per process, taken by one interpreter (the lock holder; the source calls it the owner), while everything the guardian verifies is a Python object that belongs to exactly one interpreter. The guardian's state is split along that line.

**Per-interpreter state.** One struct for each interpreter that has imported the extension: its role (none, holder or joined), its snapshot, config and resolver, the exception classes raised on its behalf, the `_in_hook` ContextVar, the code objects allowed to call `resolve()`, and for the holder the token. A struct is found through the interpreter's ID, at the cost of a thread-local read and one atomic load when a thread stays in one interpreter, and it is touched only by threads of that interpreter with its GIL held. Structs are pooled and never freed, so a pointer a thread has cached is always safe to check. The extension uses multi-phase initialisation and, from Python 3.12, declares support for interpreters that have their own GIL. Importing it again in the same interpreter (after removing it from `sys.modules`) gives another module object that works on the same struct.

**Process-wide state.** Threads of different interpreters, which may hold different GILs, read and write this at the same time. What the hook reads on every event is atomic: whether a policy is locked, the holder's interpreter ID, the policy's `log_only` flag copied at commit, and a generation counter. The rest sits behind one spinlock, inside which no Python API is called and nothing is allocated: a C-owned copy of the locked policy's serialized payload, the record of which interpreters have finished starting, and the list of structs. On POSIX the forking thread takes the spinlock before `fork()` and both processes release it afterwards, so a child process is never left with it held by a thread it does not have. One piece of process-wide state is held for much longer than a critical section, and is atomics of its own: the activation claim, by which the interpreters take turns at `activate()` and `deactivate()` (see [The policy variable](#the-policy-variable)). The holder is known by its interpreter ID, which CPython never gives out twice, and not by the address of its state, which the next interpreter created would be given: when the holder is destroyed the process stays locked and nobody is the holder.

**The startup window.** The guardian cannot authenticate Python objects: code already running in an interpreter could build stand-ins for `tethered._core` and offer those for pinning. An interpreter may therefore join only while it starts, when nothing has run in it but `site.py`, the `.pth` files and what they import. When `site.py` has processed the `.pth` files it executes `import sitecustomize`, which raises the `import` audit event with that name whether or not the module exists, and all of this happens before the call that creates the interpreter returns. The hook watches for that event in every interpreter, whether or not a policy is locked, and closes the window of the interpreter that raised it. An interpreter that already existed when the hook was first installed, which the first `activate(locked=True)` of the process does, can never join: its startup was not observed. In a process that runs without `site` (`-S`) the event never comes, so nobody joins. The record is C memory and nothing reopens a window.

**Joining.** The `tethered.pth` bootstrap of a new interpreter asks the guardian for the payload of the locked policy (`locked_payload()`). If there is one, `_core._join_locked()` rebuilds the policy and a locked `_Config` from it with the functions `activate()` uses, builds a snapshot of that interpreter's own modules, and calls `join()`. The guardian accepts when a policy is locked, the caller is not the holder, its window is open, and the offered config carries the locked policy's payload byte for byte. In one step it then binds that interpreter's `_core._config`, installs the snapshot, records the current generation and closes the window. No token is involved, and nothing is written to the policy variable. The policy comes from the guardian's copy and not from `_TETHERED_CHILD_POLICY`, so nothing done to the variable changes what is joined; inherited scopes are still read from the variable.

**Generations.** The generation counter moves when the holder commits a policy whose payload differs from the one before, and when the lock is released. A joined interpreter counts as joined only while the generation it recorded is the current one. This is how a replaced policy puts its earlier joiners outside the lock without the guardian touching their state, which belongs to other interpreters, and why re-activating an identical policy keeps them joined.

**Dispatch.** For every audit event the hook goes through these steps and stops at the first that applies:

1. Its own probe event: answer it.
2. An `import` of `sitecustomize`: close the calling interpreter's window.
3. No policy is locked, or the event is not one tethered guards: let it pass.
4. The caller is the holder: verify its snapshot (filesystem and environment events are pre-filtered first). If the snapshot holds, the holder's Python hook decides by the allow list. If the holder no longer has any state, because every instance of the extension in it has been freed, the event is refused.
5. The caller has joined, under the current generation: the same verification against its own snapshot, with its own exception classes, resolver and tamper alert. One thing differs: `os.putenv` / `os.unsetenv` of the policy variable is refused outright.
6. Anyone else: refuse the guarded operations with an exception created in the calling interpreter, reading only the atomics and the event's own arguments, never another interpreter's objects. Under a log-only lock, socket events pass.

### The policy variable

`_TETHERED_CHILD_POLICY` is one variable for the whole process, but each interpreter looks at it through its own `os.environ`, a copy made when that interpreter starts, and an `os.putenv` / `os.unsetenv` audit event reaches only the Python hook of the interpreter that raised it. With several interpreters launching children, a change made by one is invisible to the others, and so is a change made below Python. Under a lock, a launch that inherits the environment therefore also asks the guardian for the variable as the process holds it (`process_policy_env()`, which calls `getenv` or `GetEnvironmentVariableW`) and is refused when that is not the locked policy. An interpreter that has joined is refused changing the variable at all.

The interpreters of a process also take turns at changing it. `activate()` and `deactivate()` write the variable before they commit, and a write is not one step: `os.putenv` raises its audit event, every audit hook of the interpreter runs, and only then does the environment change. An interpreter could be anywhere in there while another one publishes its own policy and locks it, and its value would then land in the environment of a process whose lock it does not hold. So the guardian holds one more piece of process-wide state, the activation claim (`_guardian.activation_claim`, a context manager): whoever is about to write the variable on tethered's behalf takes it first and gives it up when its transition is committed, or has failed and been undone. That is `activate()` and `deactivate()`, locked or not, and the launch hook for the moment in which it puts the payload of an unlocked policy back into a cleaned environment (it writes only if that policy is still the active one). All of them take their interpreter's lifecycle lock first and the claim second. A thread that finds the claim taken waits for it with its GIL released, since the holder may be a thread of an interpreter that shares that GIL, and looks again once it has it: an interpreter that waited while another one locked a policy gets `TetheredLocked` before it has written anything. When several interpreters race for the first lock of a process, the winner's payload is therefore the only one that is written, and the losers are told at the door. The thread that holds the claim may take it again. The wait has no time limit, like a wait for the lifecycle lock; in the main thread a signal handler that raises ends it. Three cases are handled apart: a call made from inside a transition that the same thread is running in another interpreter raises `RuntimeError`, because that transition could not finish while the call waited for it; the claim of an interpreter that is destroyed while it holds it is given up; and a child created by `fork()` does not inherit a claim held by a thread it does not have. A call that finds the claim taken while Python is shutting down does not wait either and raises `RuntimeError`. A claim that was never given up would stop every later transition in the process, so the `with` statement is not trusted alone to give it up: Python 3.14 raises a pending exception after `__enter__` has returned and before the block is entered, and then never calls `__exit__`. Each use therefore notes how often the thread holds the claim beforehand (`held()`) and gives up anything beyond that in a `finally` (`restore()`). The claim covers the writes tethered makes. A value that application code in another interpreter assigns to `os.environ`, or that is set below Python, is met by the launch check above. The bootstrap of a new interpreter takes its turn as well, before it decides anything: it waits for a transition that is under way in another interpreter and then goes by the variable as the process holds it and by the lock as it stands, so it never acts on a policy that was published and not committed. An interpreter created while a locked policy is being replaced therefore joins the new policy. One created while the first lock of a process is being taken still stays outside it: the guardian starts to watch interpreters at that lock, so this one counts as having existed before it.

## Thread safety

`AllowPolicy` is deeply immutable after construction: rules are tuples of strings and integers, networks are stored as integers, and matching reads plain tuples, so no rule field can be reassigned in place. The `_Config` bundle is a frozen `dataclass` swapped by a single reference assignment; a hook reads `_config` once and works from that object. `activate()` and `deactivate()` are serialized from start to finish by a re-entrant lifecycle lock, so the config, the guardian state and the child-policy variable change together; `_state_lock` only guards the one-time installation of the audit hook. Installation is confirmed with the private audit event `tethered.hook_probe`, raised before adding (a hook that is already live is never added twice) and after (unanswered means another audit hook refused tethered's, and `activate()` / `scope()` raise `RuntimeError`). The IP-to-hostname map is an `OrderedDict` guarded by `_ip_map_lock` with LRU eviction. The process-wide count of active scope entries is guarded by its own lock. Reentrancy guard uses `contextvars.ContextVar` (async-safe, faster than `threading.local()`).

All of the above is per interpreter: each interpreter has its own `tethered._core` with its own locks, config and maps. Interpreters can run in parallel from Python 3.12, each under its own GIL. What they share lives in the C guardian, behind atomics and one spinlock (see [Interpreters](#interpreters)). Their `activate()` and `deactivate()` calls take turns through the guardian's activation claim (see [The policy variable](#the-policy-variable)): when several of them call `activate(locked=True)` at the same moment, one takes the lock and each of the others gets `TetheredLocked` when its turn comes.

None of this has been validated on free-threaded Python (PEP 703). The C extension does not declare free-threaded support, so importing it on a free-threaded build re-enables the GIL, and no free-threaded wheels are published.
